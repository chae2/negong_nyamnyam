# 11장 X 서비스 설계 요구사항

출처: 『요즘 개발자를 위한 시스템 설계 수업』 11장. 8절은 책의 가정으로 다시 계산한 값이다.

## 기능적 요구 사항

### 핵심 요구 사항

- **사용자 등록과 인증**
    - 사용자는 사용자 이름, 이메일, 비밀번호 등 필수 정보를 입력해 새 계정을 만들 수 있어야 한다.
    - 로그인 자격 증명은 안전하게 저장하고, 로그인할 때 인증 절차를 정확하게 처리해야 한다.
    - 사용자 세션을 효율적으로 관리해 서비스에 끊김 없이 접근할 수 있어야 한다.
- **트윗 작성**
    - 사용자는 최대 글자 수가 정해진 짧은 메시지를 작성할 수 있어야 한다. 책은 280자를 예로 든다.
    - 트윗에는 텍스트, 해시태그, 다른 사용자를 가리키는 멘션, 이미지와 동영상 같은 미디어를 넣을 수 있다.
    - 글자 수 제한을 지키고, 트윗을 빠르게 저장하고 불러올 수 있어야 한다.
- **팔로우와 언팔로우**
    - 사용자는 다른 사용자를 팔로우해 그 사용자의 트윗을 자기 타임라인에서 볼 수 있어야 한다.
    - 사용자 관계를 나타내는 팔로우 그래프를 관리할 수 있어야 한다.
    - 사용자는 언제든 언팔로우할 수 있고, 언팔로우하면 그 사용자의 트윗이 타임라인에 나타나지 않아야 한다.
- **타임라인**
    - 사용자가 팔로우하는 계정의 트윗을 시간 순서대로 보여 준다.
    - 트윗 작성 시간과 사용자 선호도를 반영해 사용자마다 맞는 타임라인을 만들어야 한다.
    - 실시간 업데이트를 지원해 새 트윗을 바로 확인할 수 있어야 한다.
- **검색**
    - 사용자는 키워드, 해시태그, 사용자 이름으로 트윗이나 다른 사용자를 검색할 수 있어야 한다.
    - 연관성, 인기, 최신성을 고려해 가장 적절한 결과를 보여 주어야 한다.
    - 트윗과 사용자 데이터를 인덱싱해 빠르고 확장 가능한 검색이 되어야 한다.
- **리트윗과 좋아요**
    - 사용자는 다른 사용자의 트윗을 자기 팔로워에게 공유(리트윗)할 수 있어야 한다.
    - 리트윗은 원본 트윗의 메타데이터와 출처 정보를 유지해야 한다.
    - 사용자는 트윗에 좋아요를 누를 수 있어야 한다.
- **다이렉트 메시지**
    - 사용자끼리 공개 트윗 피드와 별도로 개인 메시지를 주고받을 수 있어야 한다.
    - 메시지의 사생활을 보호하도록 적절한 접근 제어와 암호화가 필요하다.

## 비기능적 요구 사항

- **확장성:** 많은 사용자와 트윗을 처리하고, 사용자가 늘거나 트래픽이 몰려도 대응해야 한다. 서버를 추가해 수평으로 확장하고, 트윗 서비스와 타임라인 서비스 같은 구성 요소를 따로 확장할 수 있어야 한다.
- **가용성:** 다운타임을 최소화하고 장애가 나도 빠르게 복구해야 한다. 서버, 데이터베이스, 지역을 이중화해 서버 장애, 네트워크 단절, 데이터 센터 사고에도 사용자 경험에 큰 영향이 없어야 한다.
- **신뢰성:**
    - 데이터가 모든 구성 요소에서 정확하고 일관되게 유지되어야 한다.
    - 정기 백업이나 레플리카로 데이터 손실을 최소화해야 한다.
    - 정확성과 성능의 균형을 보고 최종 일관성과 강한 일관성 중 상황에 맞는 것을 골라야 한다. 어떤 데이터에 어느 쪽을 쓸지는 책이 정하지 않는다.
- **지연 시간:**
    - 트윗 작성, 타임라인 보기, 알림 받기 같은 핵심 기능의 지연 시간을 최대한 줄여야 한다.
    - 캐싱이나 콘텐츠 전송 네트워크(CDN)로 데이터를 빠르게 조회해야 한다.
    - 책은 지연 시간 목표값(예: 몇 ms 이내)을 제시하지 않는다.

## 설계에 사용할 추가 조건과 가정

### 1. 트윗의 입력과 결과

- `POST /tweets`: 트윗 작성
    - **입력:** 트윗 내용, 사용자 ID, 미디어 첨부 파일(선택)
    - **결과:** 새 트윗 객체(트윗 ID와 타임스탬프 포함)
- `GET /tweets/{tweetId}`: 트윗 하나 조회
    - **결과:** 트윗 객체(내용, 사용자 정보, 타임스탬프, 좋아요 수와 리트윗 수)
- `DELETE /tweets/{tweetId}`: 트윗 삭제
    - **입력:** 사용자 인증 토큰. 트윗 작성자만 삭제할 수 있다.
    - **결과:** 성공 또는 오류 메시지
- `GET /users/{userId}/tweets`: 한 사용자가 쓴 트윗 목록
    - **입력:** 사용자 ID, 페이지 매개변수(선택)
    - **결과:** 트윗 목록

### 2. 사용자, 인증, 팔로우의 입력과 결과

- `POST /users`: 계정 만들기
    - **입력:** 사용자 이름, 이메일, 비밀번호 등
    - **결과:** 사용자 객체와 사용자 ID
- `POST /auth/login`: 로그인
    - **입력:** 사용자 이름과 비밀번호 같은 자격 증명
    - **결과:** 인증 토큰(책의 예: JWT). 클라이언트는 이후 요청마다 이 토큰을 보낸다.
- `GET /users/{userId}`: 프로필 조회
    - **결과:** 사용자 이름, 소개, 프로필 사진 URL, 팔로워 수와 팔로잉 수
- `PUT /users/{userId}`: 프로필 수정
    - **입력:** 바꿀 정보(예: 소개, 프로필 사진 URL, 위치)
    - **결과:** 수정한 사용자 객체
- `POST /users/{userId}/follow`, `DELETE /users/{userId}/follow`: 팔로우와 언팔로우
    - **입력:** 사용자 인증 토큰과 대상 사용자 ID
    - **결과:** 성공 또는 오류 메시지
    - 경로의 `{userId}`가 요청한 사람인지 대상인지 책은 밝히지 않는다.
- `GET /users/{userId}/followers`, `GET /users/{userId}/following`: 팔로워 목록과 팔로잉 목록
    - **결과:** 사용자 객체 목록

### 3. 타임라인과 검색의 입력과 결과

- `GET /timeline/{userId}`: 홈 타임라인
    - **입력:** 사용자 인증 토큰
    - **결과:** 트윗 객체 목록. 타임스탬프 기준 최신순으로 정렬한다.
- `GET /timeline/{userId}/mentions`: 그 사용자가 멘션된 트윗 목록
    - **입력:** 사용자 인증 토큰
    - **결과:** 멘션된 트윗 객체 목록
- **타임라인 길이:** 사용자마다 최근 트윗 ID를 일정 시간 범위나 최대 개수로 제한해 유지한다고 설명한다. 구체적인 범위나 개수는 제시하지 않는다.
- `GET /search/tweets?q={query}&limit={limit}&offset={offset}`: 트윗 검색
- `GET /search/users?q={query}&limit={limit}&offset={offset}`: 사용자 검색
    - **입력:** 검색어 `q`. `limit`과 `offset`은 선택이다.
    - **결과:** 검색어와 맞는 트윗 또는 사용자 목록. 연관성이나 인기도로 순위를 매긴다.

### 4. 책이 정하지 않은 것

- 좋아요, 리트윗, 다이렉트 메시지는 기능 요구와 데이터 모델에는 있지만 API 예시가 없다.
- 타임라인에 "사용자 선호도를 반영"한다고 하지만, 조회 과정은 타임스탬프 최신순 정렬만 설명한다.
- 트래픽 폭주 배수를 제시하지 않는다. "인프라는 최대 부하를 처리할 수 있도록 설계"해야 한다고만 쓴다.

### 5. 데이터 모델

책의 UML 클래스 다이어그램(그림 11-1)에 있는 엔티티는 다음과 같다.

- **User:** `user_id`(기본 키), 사용자 이름, 이메일, 비밀번호 해시, 프로필 사진, 소개글, 위치, 웹 사이트
- **Tweet:** `tweet_id`(기본 키), 내용, 작성자 `user_id`, 작성 시각, 미디어 URL(첨부한 경우), 위치 정보, 리트윗 수, 좋아요 수
- **Follow:** `follower_id`, `followee_id`, `created_at`
- **Like:** `user_id`(누른 사람), `tweet_id`(받은 트윗), `created_at`
- **Retweet:** `tweet_id`(원본 트윗), `retweeted_by_user_id`, `created_at`
- **DirectMessage:** `message_id`, `sender_id`, `recipient_id`, `content`, `created_at`

### 6. 사용자 규모와 이용 패턴

다음 수치는 책에서 계산을 위해 둔 가정이다.

- **전체 사용자:** 1억 명이다.
- **하루 활성 사용자(DAU):** 2,000만 명이다(전체의 20%).
- **트윗 작성:** DAU 1명당 하루 5개, 하루 1억 개다.
- **트윗 크기:** 평균 200바이트다.
- **미디어:** 전체 트윗의 20%가 미디어를 포함하며 평균 크기는 1MB다.
- **보관 기간:** 트윗을 5년 보관한다.
- **평균 팔로워:** 100명이다. 대역폭과 팬아웃 계산에 쓴다.
- **타임라인 조회:** DAU 1명당 하루 100번, 하루 20억 번이다.
- **캐시 적중률:** 80%로 가정한다.
- **사용자 데이터:** 프로필 사진, 소개글 등을 합쳐 1명당 1MB로 가정한다.

### 7. 책의 규모 산정 결과

| 항목 | 책의 계산 | 책의 값 |
|---|---|---|
| 트윗 저장 | 1억 개 × 200바이트 | 하루 20GB, 1년 7.3TB, 5년 36.5TB |
| 미디어 저장 | 1억 개 × 20% × 1MB | 하루 200TB, 1년 73PB, 5년 365PB (8번 참고) |
| 사용자 저장 | 1억 명 × 1MB | 100TB |
| 전체 저장 | 위 세 항목의 합 | 약 365PB |
| 트윗 전달량 | 1억 개 × 팔로워 100명 × 200바이트 | 하루 100억 건, 2TB |
| 미디어 전달량 | 2,000만 개 × 팔로워 100명 × 1MB | 하루 20억 건, 2PB |
| 하루 대역폭 | 트윗 2TB + 미디어 2PB | 약 2PB |
| 초당 트윗 | 1억 개 ÷ 86,400초 | 약 1,200건 |
| 초당 미디어 업로드 | 초당 트윗 × 20% | 약 240건 |
| 팬아웃 | 초당 트윗 × 팔로워 100명 | 초당 약 12만 건 |
| 캐시 크기 | 조회 20억 번 × 80% × 200바이트 | 약 320GB |

### 8. 책 계산을 다시 확인한 것

이 절의 값은 책의 가정으로 내가 다시 계산한 것이다.

- **미디어 저장량이 10배 크게 적혀 있다:** 1억 개 × 20% × 1MB는 하루 미디어 2,000만 개, 20TB다. 책은 200TB로 적었다. 다시 계산하면 1년 7.3PB, 5년 36.5PB이고 전체 저장은 약 36.6PB다. 책의 미디어 전달량(하루 20억 건)도 하루 미디어 2,000만 개를 전제로 계산되어 있다.
- **"초당 최대 트윗 수"는 하루 평균이다:** 1억 ÷ 86,400 ≈ 초당 1,157건이다. 최대값이 아니므로 폭주 상황의 수치는 따로 정해야 한다.
- **책이 계산하지 않은 읽기량:** 타임라인 조회 하루 20억 번은 평균 초당 약 2.3만 건이다. 트윗 작성(초당 약 1,157건)의 약 20배다.
- **책이 계산하지 않은 전송 속도:** 하루 2PB는 평균 초당 약 23GB(약 185Gbps)다.
