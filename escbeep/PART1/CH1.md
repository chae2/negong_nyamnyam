# 1장. 시스템 설계의 기본

## 1.1 시스템 설계의 정의

소프트웨어 시스템은 특정 작업이나 일련의 작업을 수행하려고 함께 동작하는 컴포넌트나 모듈, 프로그램의 집합이다.  
일반적으로 데이터 관리, 트랜잭션 처리, 최종 사용자를 위한 서비스 제공 등 원하는 기능을 실행할 수 있는 연관된 소프트웨어 애플리케이션으로 구성된다.  
애플리케이션을 개발할 때는 어떤 프로그래밍 언어를 선택할지, 어떤 에디터를 사용할지, 테스트는 TDD 방식으로 할지 등 다양한 고민을 하게 된다.  

분산 소프트웨어 시스템은 여러 독립적인 컴포넌트나 프로세스, 노드로 구성할 수 있는데 이들은 서로 통신을 주고받으며 하나의 공동 목표를 달성하려고 동작한다.  
모든 구성 요소가 하나의 기기에 위치한 중앙 집중현 소프트웨어 시스템과 달리, 분산 소프트웨어 시스템은 지리적으로 다른 위치에 있는 여러 기기와 네트워크에 걸쳐 있다.  
분산 시스템의 각 구성 요소는 특정 작업이나 일련의 작업 모음을 처리하며, 모두 하나의 공통 목표를 달성하려고 동작한다.  
각 구성 요소끼리는 원격 프로시저 호출(RPC), 메시지 전달, pub/sub 모델 등 다양한 통신 프로토콜을 통해 서로 소통한다.  
분산 시스템은 주로 확장성, 가용성, 장애 허용이 중요한 요구 사항으로 등장하는 대규모 애플리케이션을 구축할 때 사용하며 클라우드 컴퓨팅 플랫폼, P2P 네트워크, 분산 데이터베이스, 콘텐츠 전송 네트워크(CDN) 등이 있다.  

시스템 설계는 소프트웨어 시스템의 아키텍처, 컴포넌트, 모듈, 인터페이스 및 상호 작용을 정의하여 기능적·비기능적 요구 사항을 채우는 과정이다.  
소프트웨어 시스템 설계의 목표는 이해하기 쉽고 유지 보수와 확장이 용이하며 시스템의 성능, 확장성, 신뢰성, 보안 요구 사항을 지킬 수 있는 설계를 만드는 것이다.  

시스템 설계는 보통 다음 과정을 거친다.
1. 요구 사항 분석: 시스템의 기능적·비기능적 요구 사항을 면밀히 분석하고 이해하는 과정입, 데이터 조회와 저장 패턴을 심도있게 분석하여 패턴을 활용할 수 있도록 설계하는 작업도 포함
2. 상위 수준의 아키텍처 설계: 시스템의 전반적인 구조를 설계하는 과정으로 컴포넌트, 모듈, 인터페이스 등을 정의
3. 하위 수준의 상세 설계: 시스템의 내부 구조와 동작을 설계하는 단계, 각 컴포넌트의 핵심 비즈니스 로직을 구현할 알고리즘을 정의하고, 컴포넌트 간 상호 작용을 설계
4. 사용자 인터페이스 설계: API 통신을 통해 백엔드 서비스와 소통할 사용자 인터페이스를 정의
5. API 설계: 사용자 인터페이스 또는 프런트엔드가 백엔드 서비스와 상호 작용할 수 있도록 적절한 API를 정의
6. 데이터베이스 설계: 시스템에서 사용하는 데이터 구조와 저장 메커니즘을 설계, 간단한 파일 저장소와 관계형 데이터베이스, NoSQL 데이터베이스 중 적절한 것을 선택

결과물로는 아키텍처 다이어그램이나 상세 설계 문서처럼 API와 사용자 인터페이스 프로토콜을 나열하고 정의한 일련의 설계 문서가 나온다. 이런 문서는 소프트웨어 시스템을 구현하는 일종의 길잡이 역할을 한다.

## 1.2 시스템 설계의 다양한 유형

시스템 설계는 크게 상위 수준의 아키텍처 설계와 하위 수준의 상세 설계로 나뉜다. 상위 수준 설계에서는 시스템을 어떤 구성 요소로 나누고 어떻게 연결할지 결정한다. 하위 수준 설계에서는 각 구성 요소가 실제로 데이터를 처리하는 방법과 인터페이스를 구체화한다. 두 단계는 순서대로 한 번씩 끝내는 작업이 아니다. 상세 설계 과정에서 병목이나 구현 제약을 발견하면 상위 구조를 다시 조정할 수 있다.

| 구분 | 주로 답하는 질문 | 결과물의 예 |
| --- | --- | --- |
| 상위 수준 설계 | 어떤 구성 요소가 필요하며 데이터와 요청은 어디로 흐르는가? | 아키텍처 다이어그램, 서비스 경계, 데이터 흐름, 확장·장애 대응 방안 |
| 하위 수준 설계 | 각 구성 요소는 어떤 자료구조, 알고리즘, API로 동작하는가? | API 명세, 데이터 모델, 처리 절차, 오류 처리 및 최적화 방식 |

### 1.2.1 상위 수준의 시스템 설계

#### 시스템 아키텍처

아키텍처는 주요 구성 요소, 구성 요소 사이의 책임, 통신 방법을 정한 전체 구조다.

- **모놀리식:** 여러 기능을 하나의 애플리케이션에 묶는다. 구성과 배포가 단순하지만, 기능과 팀이 커지면 일부 기능만 독립적으로 변경하거나 확장하기 어려울 수 있다.
- **클라이언트·서버:** 클라이언트가 서버에 요청하고 서버가 데이터를 처리해 응답한다. 사용자 인터페이스와 서버 측 처리를 나누는 기본적인 구조다.
- **마이크로서비스:** 기능을 여러 독립 서비스로 나누고 네트워크로 통신한다. 서비스별 개발과 확장이 가능하지만 서비스 간 호출, 데이터 일관성, 운영 복잡성을 관리해야 한다.
- **이벤트 주도:** 구성 요소가 메시지나 이벤트를 발행하고 다른 구성 요소가 이를 처리한다. 호출자와 처리자를 느슨하게 연결할 수 있지만, 처리 순서와 재시도, 중복 이벤트를 고려해야 한다.

어떤 구조가 언제나 우월한 것은 아니다. 확장성, 유지 보수성, 신뢰성, 지연 시간을 함께 놓고 선택한다.  
예를 들어 주문 기능을 별도 서비스로 나누면 주문 처리량에 맞춰 독립적으로 확장할 수 있지만, 결제 및 재고 서비스와의 통신과 실패 처리가 설계 과제로 추가된다.

#### 데이터 흐름

상위 설계에서는 데이터가 **수집 → 저장 → 처리 → 검색**되는 경로를 따라가며 각 단계의 책임을 정한다.

1. **수집:** 사용자의 API 요청, 외부 시스템의 이벤트, 주기적 배치 중 어떤 방식으로 데이터가 들어오는지 확인한다. 입력량과 입력 데이터의 검증 방법도 함께 살핀다.
2. **저장:** 읽기와 쓰기 빈도, 검색 조건, 일관성 요구에 맞는 저장 방식을 선택한다. 모든 데이터를 한 저장소에 넣는 대신 용도에 따라 별도의 저장 경로를 둘 수도 있다.
3. **처리:** 변환, 집계, 분석이 동기적으로 이루어져야 하는지 결정한다. 처리량과 계산 비용이 크다면 비동기 처리나 병렬 처리를 고려한다.
4. **검색:** 사용자가 처리 결과를 어떤 조건으로 얼마나 빨리 조회해야 하는지 정한다. 필요한 경우 인덱스, 캐시, 읽기 복제본을 활용한다.

각 단계의 평균 처리 시간만 보아서는 충분하지 않다. 특정 단계에 요청이 쌓이면 다음 단계가 아무리 빨라도 전체 응답이 느려진다. 따라서 흐름 전체에서 병목과 장애 전파 경로를 확인해야 한다.

#### 확장성

확장성은 작업량이 늘어났을 때 시스템이 필요한 처리량을 확보할 수 있는 능력이다.  
**수직 확장**은 서버 한 대의 CPU, 메모리, 저장소를 늘린다. 구조를 크게 바꾸지 않아도 되지만 장비의 상한에 도달할 수 있다.  
**수평 확장**은 서버나 인스턴스를 추가해 작업을 나눈다. 처리량과 장애 대응 능력을 키우기 쉽지만 요청 분배와 데이터 조정이 필요하다.

웹 요청을 여러 서버로 나누려면 로드 밸런서가 필요하다. 자주 읽는 데이터는 캐시로 저장소 부하를 줄일 수 있고, 데이터 양 자체가 커지면 데이터베이스를 분할할 수 있다.  
애플리케이션 서버가 특정 인스턴스에만 사용자 상태를 저장하지 않도록 설계하면 서버를 추가하거나 교체하기 쉽다.  
이런 방법은 각기 다른 병목을 해결하므로, 먼저 어떤 자원이 부족한지 파악해야 한다.

#### 장애 허용성

장애 허용성은 구성 요소 일부가 실패해도 서비스가 필요한 기능을 계속 제공하는 능력이다. 데이터나 서버를 복제하고, 단일 장애점이 되는 구성 요소에는 대체 경로를 둔다.  
모니터링과 헬스 체크로 장애를 감지한 뒤 요청을 정상 인스턴스로 전환할 수 있어야 한다.

모든 기능을 항상 정상 수준으로 유지하기 어려울 때는 **점진적 성능 저하**도 선택할 수 있다. 예를 들어 추천 서비스가 실패해도 상품 조회와 결제는 유지하고 추천 영역만 기본 목록으로 대체한다.  
장애 허용 설계에서는 무엇을 계속 제공해야 하는지, 어떤 기능을 일시적으로 축소할 수 있는지 먼저 정해야 한다.

### 1.2.2 하위 수준의 상세 설계

상위 설계가 구성 요소 사이의 관계를 정했다면, 상세 설계는 각 구성 요소의 내부 동작을 정한다.

#### 알고리즘

알고리즘을 고를 때는 입력이 늘어날수록 실행 시간이 어떻게 증가하는지 나타내는 **시간 복잡도**와 메모리 사용량이 어떻게 증가하는지 나타내는 **공간 복잡도**를 함께 검토한다. 빠른 조회를 위해 인덱스나 캐시를 추가하면 메모리를 더 쓰고 쓰기 작업도 복잡해질 수 있다. 가장 빠른 알고리즘을 무조건 고르기보다 현재 작업의 읽기, 쓰기 비율과 자원 제한을 기준으로 선택한다.

#### 데이터 구조

데이터 접근 방식에 따라 쿼리 성능(시간 복잡도)와 메모리 사용량을 계산해 가장 적절한 방식을 택해야 한다.  
자료구조도 접근 패턴에 따라 달라진다. 배열은 순차 접근과 인덱스 조회에, 해시 테이블은 키 기반 조회에, 트리는 정렬된 범위 검색에 적합한 경우가 많다. 검색, 삽입, 삭제가 각각 얼마나 자주 일어나는지와 데이터 크기를 함께 확인해야 한다. 같은 기능을 구현해도 자료구조 선택에 따라 메모리 사용량과 응답 시간이 크게 달라진다.

#### API 설계

API는 구성 요소 사이의 계약이다. 요청 형식, 응답 형식, 오류의 의미를 일관되게 정하면 호출자가 내부 구현을 몰라도 서비스를 사용할 수 있다. API를 설계할 때는 다음을 확인한다.

- 일관성: 이름과 응답 구조가 전체 서비스에서 일관되게 사용되는가?
- 유연성: 변경이 기존 클라이언트를 깨뜨리지 않는가?
- 보안: 인증, 인가와 입력값 검증이 필요한 위치에 적용되는가?
- 성능: 응답 시간과 데이터 크기가 요구 사항에 맞는가?

예를 들어 `/api/v1/users`의 응답 구조를 바로 바꾸면 이전 버전의 클라이언트가 오류를 낼 수 있다. 새 구조가 필요하다면 새 버전을 제공하고 클라이언트를 순차적으로 전환한 뒤 이전 버전을 종료하는 방식이 가능하다. 버전 번호 자체보다 **기존 사용자와 새 사용자가 전환 기간에 함께 동작할 수 있게 하는 것**이 중요하다.

#### 코드 최적화

- 리팩터링: 외부 동작을 유지하며 코드를 읽고 고치기 쉽게 만든다.
- 메모이제이션: 같은 계산의 결과를 재사용한다. 캐시한 결과는 언제 갱신할지 정해야 한다.
- 병렬 처리: 독립적인 작업을 동시에 수행한다. 병렬 작업에는 동기화 비용이 발생한다. 
- 루프 언롤링: 반복문의 일부를 펼쳐 반복 제어 비용을 줄이지만 코드가 길어질 수 있다. 루프 언롤링처럼 낮은 수준의 최적화는 실제 병목을 측정한 뒤 효과가 있을 때 적용하는 편이 좋다.
    - 예시: 샌드위치를 만들 때 빵 → 야채 → 햄 → 빵의 순서를 n번 반복하는 것이 아니라, n개의 빵을 한번에 펼치고 그 위에 n개의 야채를 올리는 식으로 샌드위치를 한 번에 만든다.

상세 설계의 목표는 성능만 높이는 것이 아니라 기능, 가독성, 유지 보수성을 함께 만족시키는 것이다.

## 1.3 업계에서 시스템 설계가 갖는 중요성

시스템을 설계하는 과정은 요구 사항을 구체적인 선택으로 바꾸는 과정이기도 하다.  
단순히 빠른 서비스를 만들겠다고 정하는 데 그치지 않고, 어떤 작업이 얼마나 빨라야 하는지, 장애가 나면 무엇을 유지해야 하는지, 어떤 데이터가 정확해야 하는지 합의하게 된다.  
이 기준이 있어야 아키텍처의 적합성을 검토할 수 있다.

설계 문서는 팀 내부와 이해관계자 사이의 공통 언어가 된다. 전체 구조와 데이터 흐름이 보이면 구현 담당자들이 서로 다른 전제를 가지고 작업하는 일을 줄일 수 있다.  
설계 검토에서는 병목, 보안 위험, 데이터 불일치, 변경이 어려운 결합 관계를 구현 전에 찾아낼 수 있다.

운영 단계에서도 설계의 영향이 이어진다. 자원을 추가할 수 있는 구조라면 트래픽 증가에 대응하기 쉽고, 구성 요소의 책임이 분명하면 장애 범위를 파악하고 수정하기 쉽다. 그 결과 재작업과 운영 비용을 줄일 수 있다.  
반대로 설계에 시간을 썼다는 사실만으로 좋은 결과가 보장되는 것은 아니므로, 선택한 구조가 실제 요구 사항을 충족하는지 계속 검증해야 한다.

## 1.4 시스템 설계의 중요성을 엿볼 수 있는 실제 사례

| 분야 | 시스템이 처리하는 일 | 설계에서 특히 중요한 점 |
| --- | --- | --- |
| 금융 | 계좌 잔액, 거래 내역, 송금 등을 기록한다. | 잘못된 중복 처리와 데이터 손실을 막고, 거래 상태를 일관되게 유지해야 한다. |
| 전자상거래 | 상품 조회, 주문, 재고, 결제, 배송을 연결한다. | 조회 트래픽과 주문 트랜잭션의 요구가 다르므로 기능별 확장과 장애 처리를 구분해야 한다. |
| 의료 | 진료 기록과 의료 영상을 저장하고 조회한다. | 민감한 정보의 접근 권한, 보존, 신뢰성, 규제 요구를 충족해야 한다. |
| 제조 | 생산 공정을 제어하고 설비와 재고를 추적한다. | 설비 상태를 제때 반영하고 여러 시스템의 데이터를 일관되게 연결해야 한다. |
| 운송 | 배송 상태를 추적하고 경로를 계산한다. | 많은 위치·상태 정보를 처리하면서 지연과 장애에 대응해야 한다. |

분야별로 우선순위는 다르다. 금융 거래에서는 정확한 상태 변경이 핵심일 수 있고, 상품 검색에서는 대량 조회와 빠른 응답이 더 중요할 수 있다.  
좋은 설계는 모든 속성을 최대로 만드는 것이 아니라 **서비스에서 실패하면 안 되는 일이 무엇인지**를 명확히 하고 자원을 그에 맞게 배분한다.
