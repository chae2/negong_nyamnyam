발표자 메모 · 실제 클릭 순서

“화면에는 같은 시각에 처리한 세 주문의 로그가 섞여 있습니다. 시간순으로만 읽으면 주문 A의 시작과 주문 B의 완료를 잘못 연결할 수 있습니다. 먼저 느린 주문 A를 고르면 두 서비스의 로그가 하나의 요청으로 모입니다.”

“여기서 WARN만 고르면 DB 호출이 오래 걸렸다는 사건이 나옵니다. 하지만 이 로그만으로 DB 서버가 느렸다고 확정할 수는 없습니다. 연결을 기다렸거나 네트워크에서 지연됐을 수도 있습니다. 로그는 다음 확인 대상을 좁힐 근거입니다.”

“이제 ERROR를 선택해 보겠습니다. 아무 기록도 없습니다. 이 요청은 느렸지만 성공했기 때문입니다. 오류 로그가 없다는 사실만으로 서비스 품질이 정상이라고 판단하면 안 됩니다.”

클릭: 요청 → 느린 주문 A → 레벨 WARN → 레벨 ERROR → 모든 레벨 → 구조화된 로그 펼치기. 확인: 7개 → 1개 → 0개로 바뀌는 기록 수를 짚습니다. 마지막 30초에는 시각만으로 요청을 연결하기 어려운 이유를 질문합니다.

로그 저장소가 멈추면 어떻게 될까?

수집기와 저장소 사이에 버퍼를 두면 잠시 쌓인 데이터를 보관할 수 있습니다. 버퍼의 용량, 저장 방식, 수신 확인과 재시도를 함께 정해야 합니다.

이 모형의 가정과 실제 Logstash PQ의 차이
  • 큐에 넣은 이벤트는 수신 확인을 마쳤다고 가정합니다. 큐가 가득 차면 새 이벤트는 애플리케이션에 남습니다. 이는 생산자가 재시도와 보관을 지원하는 경우의 역압력 예시입니다.
  • 디스크 모드에서는 체크포인트까지 완료한 이벤트만 다룹니다. 수집기 재시작은 디스크 손상을 뜻하지 않습니다.
  • 실제 Logstash의 Persistent Queue는 기본적으로 꺼져 있습니다. 수신 확인이 없는 입력, 체크포인트 전 장애, 디스크 손상 등에서는 데이터가 유실될 수 있습니다.
  • ACK를 잃으면 이미 저장한 이벤트를 다시 보낼 수 있습니다. 이 모형의 저장소는 중복을 제거하지 않습니다. 고유 이벤트 ID를 이용한 중복 처리 전략이 별도로 필요합니다.

발표자 메모 · 메모리와 디스크 비교

“저장소가 멈춘 상태에서 로그 여섯 개를 만들어 보겠습니다. 다섯 개는 수집기 큐에 있고 하나는 생산자에 남습니다. 메모리 큐에서 수집기를 재시작하면 다섯 개가 사라집니다. 디스크 모드로 같은 과정을 반복하면 이 모형에서는 다섯 개가 남습니다.”

“디스크에 썼다는 이유만으로 모든 장애에서 안전한 것은 아닙니다. 체크포인트와 디스크 자체의 장애를 고려해야 합니다. 저장 후 ACK만 사라지면 재시도로 중복이 생기는 것도 확인할 수 있습니다. 로그 파이프라인에서도 전달 보장 문제를 만나게 됩니다.”

클릭: 저장소 중단 → 로그 3개 생성 두 번 → 수집기 재시작. 저장 방식을 디스크로 변경하면 시연이 초기화됩니다. 같은 순서 반복 → 저장소 복구·전송 → ACK 유실·재시도. 확인: 디스크 모드의 저장 레코드는 6→7개, 고유 이벤트는 6개로 유지됩니다.

무엇을 세고, 무엇을 측정할까?

책은 시스템·애플리케이션·비즈니스 메트릭을 구분합니다. 여기에 데이터를 기록하는 형식인 Counter·Gauge·Histogram을 연결합니다. 관측 대상의 분류와 메트릭 형식은 서로 다른 기준입니다.

Counter · 완료 횟수

완료한 요청을 누적합니다. 프로세스 재시작 등으로 초기화될 수 있습니다.

completed_requests_total

Gauge · 현재 상태

지금 처리 중인 요청 수처럼 증가하거나 감소하는 값을 기록합니다.

requests_in_progress

Histogram · 분포

완료한 요청의 응답 시간을 구간별로 집계합니다. 다음 구간에서 직접 비교합니다.

request_duration_seconds
완료 Counter0
진행 중 Gauge0
Histogram에 기록한 관측 수0

요청 시작 시 Gauge를 늘립니다. 완료 시 Gauge를 줄이고 Counter와 Histogram의 관측 수를 늘립니다. 이 모형은 완료 시점에 요청을 집계합니다.

대시보드의 첫 세 지표: 요청 속도·오류 비율·응답 시간
  • 요청 속도: 누적 Counter의 증가율을 봅니다. 예를 들어 10초 동안 100개가 완료되면 평균 10건/초입니다.
  • 오류 비율: 같은 기간과 범위에서 실패 횟수를 전체 완료 횟수로 나눕니다. 요청이 없을 때와 수집이 끊겼을 때도 구분해야 합니다.
  • 응답 시간: 성공과 실패를 구분해 분포를 살펴봅니다. 빠르게 실패한 요청이 많으면 전체 평균이 낮아질 수도 있습니다.

Prometheus에서는 Counter의 증가율에 rate()를 사용합니다. Gauge에 같은 의미로 적용하지 않습니다.

책: 8.6.1, 8.6.3 · 보충: Prometheus 계측 지침

발표자 메모 · 같은 요청을 세 가지 형식으로 보기

“CPU나 주문 건수는 무엇을 측정하는지에 따른 구분입니다. Counter와 Gauge는 어떤 형태로 값을 기록하는지에 따른 구분입니다. 여기서는 완료한 요청을 Counter로, 처리 중인 요청을 Gauge로 기록합니다.”

“요청 세 개를 시작하면 Gauge만 3이 됩니다. 하나를 완료하면 Gauge는 2로 줄고 완료 Counter는 1이 됩니다. 이때 응답 시간도 Histogram에 관측 한 건으로 기록합니다. 누적 완료 횟수만 보면 지금 바쁜지 알기 어려우므로 증가율과 진행 중 요청도 함께 봅니다.”

클릭: 요청 시작 세 번 → 요청 1개 완료 한 번 → 남은 요청 두 개 완료. 확인: Gauge는 0으로 돌아가지만 Counter와 관측 수는 3으로 남습니다.

Classic Histogram 예시입니다. 같은 요청이 여러 누적 버킷에 포함되므로 모든 버킷 값을 더하지 않습니다.

이름과 라벨은 실습용으로 직접 정의했습니다. 실제 환경의 계측 이름에 맞춰 바꿔야 합니다. 호환되는 버킷을 가진 인스턴스의 분포를 합친 뒤 p95를 추정합니다.

계산 차이: 위 카드의 p95·p99는 정렬한 원본 표본의 ceil(q × N)번째 값입니다. Prometheus의 Histogram은 버킷을 이용해 백분위수를 추정하므로 버킷 경계와 해상도에 따라 값이 달라질 수 있습니다.

서버별 p95를 평균 내면 전체 p95가 되지 않습니다. 분포를 먼저 합쳐야 합니다. Native Histogram은 동적 버킷을 지원하며 공식 문서는 지원 환경에서 이를 권장합니다. 여기서는 누적 버킷을 설명하기 위해 Classic 형식을 사용합니다.

발표자 메모 · 평균 계산과 경계 사례

“정상 요청만 있을 때는 모든 값이 100 ms입니다. 10%를 느리게 만들면 평균은 290 ms입니다. 계산은 90개 곱하기 100에 10개 곱하기 2,000을 더하고 100으로 나눈 것입니다. 평균은 300 ms보다 작지만 열 명 중 한 명은 2초를 기다립니다.”

“이번에는 느린 요청을 1%로 줄이겠습니다. 표본 100개에서 최근접 순위 방식으로 계산한 p99는 99번째 값이므로 여전히 100 ms입니다. 최댓값은 2,000 ms입니다. p99 하나도 모든 요청을 대표하지는 않습니다.”

“실제 Prometheus에서는 원본 요청을 모두 저장하지 않고 Histogram 버킷으로 계산할 수 있습니다. 이 경우 화면의 정확한 표본 순위와 추정값을 구분해야 합니다. 여러 서버의 결과를 합칠 때도 각 서버의 p95를 평균 내지 않고 분포를 합칩니다.”

조건을 넘는 순간 바로 호출할까?

책은 중요도·실행 가능성·진단 정보를 갖춘 알림을 제시합니다. 심화에서는 조건이 성립하는 시간과 알림 전달 방식을 나누어 살펴봅니다.

평가된 오류 비율
조건 최초 성립 이후
규칙 상태

조건: 최근 5분 오류 비율 > 1%, for: 2m. 그래프 값은 이미 계산된 5분 오류 비율의 가상 평가 결과입니다. 평가 간격은 1분이며 5분 집계 창과 2분 유지 시간은 별개입니다. 별도의 keep_firing_for는 설정하지 않았습니다.

예시 규칙과 Alertmanager의 역할
groups:
  - name: order-study
    interval: 1m
    rules:
      - alert: OrderErrorRatioHigh
        expr: |
          sum(rate(completed_requests_total{service="order-api",outcome="error"}[5m]))
          / sum(rate(completed_requests_total{service="order-api"}[5m])) > 0.01
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "주문 API의 오류 비율 상승"

위 이름은 실습용 메트릭입니다. 이 규칙만으로 트래픽 부족이나 계측 중단을 구분하지 못하므로 실제 적용 시 별도 조건과 규칙이 필요합니다.

  • Grouping: 관련 알림들을 묶어서 한 알림 메시지로 전달합니다.
  • Silence: 정한 시간 동안 선택한 알림의 통지를 중지합니다.
  • Inhibition: 상위 장애 알림이 발생한 동안 관련 하위 알림의 통지를 억제합니다.

이 전달 예시는 Firing 알림 3개가 있다고 별도로 가정합니다. 위의 규칙 상태를 바꾸지 않으며 그룹 대기 시간도 생략했습니다.

실패 비율이 같아도 목표에 따라 다르다

SLI · 측정값

예: 유효한 주문 요청 중 성공한 요청의 비율입니다. 성공과 측정 범위를 먼저 정의합니다.

SLO · 목표

예: 최근 30일의 성공률 99.9%입니다. 30일 동안의 목표와 짧은 관측 창을 구분합니다.

오류 예산

이 성공률 목표에서 허용하는 실패 비율은 0.1%입니다. 실제 허용 실패 건수는 요청 수에 따라 달라집니다.

허용 실패 비율
1시간 / 5분 소진 속도
두 창 모두 14.4배 초과?

소진 속도 = 관측한 실패 비율 ÷ (1 − SLO)

계산에서는 비율 단위를 일치시킵니다. 99.9% 목표에서 실패 비율 1%는 1 ÷ 0.1 = 10배입니다. 이 시연은 1시간과 5분을 함께 보는 알림 한 경로만 다루며, 장시간 완만한 소진을 감지하는 전체 운영 정책을 구현한 것은 아닙니다.

왜 두 관측 창을 함께 볼까?

긴 창은 충분한 규모의 오류가 발생했는지 살피고, 짧은 창은 문제가 지금도 계속되는지 확인합니다. 이미 회복했는데 과거 오류가 긴 창에 남아 있는 상황을 구분하는 데 도움이 됩니다.

30일 목표에서 1시간 동안 14.4배로 소진하면, 요청량이 일정하다는 가정 아래 전체 오류 예산의 약 2%를 소비합니다. 낮은 트래픽에서는 단 한 번의 오류도 비율을 크게 바꾸므로 요청 수와 사용자 영향을 함께 봐야 합니다. 임계값은 서비스 상황에 맞게 정합니다.

최종 보관 Trace
오류 Trace 보관 / 전체 오류
지연 Trace 보관 / 전체 지연

반복 가능한 비교를 위해 Head 예시는 ID 1·4·8을 선택하도록 고정했습니다. 실제 난수 또는 Trace ID 해시 알고리즘을 구현한 것은 아닙니다. Tail 예시는 10개 Trace가 모두 완전하게 도착한 뒤 판단하며, 오류가 있는 Trace와 1초 초과 Trace만 보관합니다.

    알림에 연결할 짧은 Runbook
    1. 영향 확인: 대상 서비스, 경로, 배포 버전, 발생 시각과 요청 수를 확인합니다. 성공과 실패 응답의 지연을 나눠 봅니다.
    2. 범위 축소: 전체 인스턴스에서 나타나는지, 특정 경로나 인스턴스에 집중되는지 비교합니다.
    3. 요청 추적: 대표적인 느린 요청 또는 실패 요청의 Trace ID를 찾습니다. 표본 추출 정책 때문에 대표성이 달라질 수 있음을 확인합니다.
    4. 근거 대조: 긴 Span의 서비스 로그, DB 지표, 최근 변경 기록을 확인합니다. 근거가 확인된 가설에 맞춰 대응합니다.
    5. 복구 확인: 새 요청의 결과와 집계 창의 지표를 함께 확인합니다. 알림 해제 여부와 재발 여부를 확인하고 기록합니다.
