# 4장. 분산 시스템의 기본 요소: DNS, 로드 밸런서, 애플리케이션 게이트웨이

앞 장이 분산 시스템의 속성과 이론을 설명했다면, 이 장은 사용자의 요청이 실제 서비스에 도달하는 경로에 놓이는 구성 요소를 다룬다. **DNS**는 서비스의 주소를 찾고, **로드 밸런서**는 여러 서버로 요청을 분배하며, **애플리케이션 게이트웨이**는 요청의 내용에 따라 공통 정책과 라우팅을 적용한다. 기능이 일부 겹치더라도 각 계층에서 해결하려는 문제가 다르다.

책이 이 장에서 다루는 기본 요소는 다음과 같다.

- **DNS:** 도메인 이름에서 접속할 주소를 찾는다.
- **로드 밸런서:** 여러 서버와 지역으로 요청을 나눈다.
- **애플리케이션 게이트웨이:** 애플리케이션 요청을 라우팅하고 공통 정책을 적용한다.

## 4.1 DNS 이해

DNS(Domain Name System)는 사람이 사용하는 도메인 이름에 대응하는 주소와 정보를 찾는 분산된 이름 체계다. 사용자가 웹 주소를 입력하면 브라우저는 서버와 통신하기 위해 이름에 연결된 주소를 알아내야 한다. DNS는 수많은 네임 서버가 담당 범위를 나누고 서로를 가리키는 계층 구조로 이 일을 수행한다.

사용자가 `www.example.com`을 입력할 때 브라우저가 최종적으로 필요한 것은 접속할 목적지의 주소다. DNS 조회로 주소를 얻은 다음에야 그 주소로 연결을 시작한다. DNS가 웹 콘텐츠를 전달하는 것은 아니며, 도메인과 연결된 레코드를 알려 주는 역할을 한다. 이 과정이 브라우저 뒤에서 이루어져 사용자가 도메인 이름만 기억해도 서비스에 접근할 수 있다.

DNS를 구성하는 요소를 다음과 같이 나눈다.

- **네임 서버:** 사용자의 DNS 질의에 답하는 서버다. DNS는 한 대가 아니라 여러 네임 서버가 담당 범위를 나누는 구조다.
- **리소스 레코드:** 이름과 관련 정보를 저장하는 단위다. 주요 유형은 다음과 같다.
  - **`A`:** 호스트 이름을 IPv4 주소에 연결한다. 예를 들어 `api.example.com`의 접속 주소를 알려 준다.
  - **`NS`:** 해당 도메인을 담당하는 권한 있는 네임 서버를 가리킨다.
  - **`CNAME`:** 별칭을 정식 도메인 이름에 연결한다.
  - **`MX`:** 해당 도메인으로 오는 메일을 받을 서버를 지정한다.
- **캐싱:** 한 번 찾은 레코드를 여러 위치에 보관해 같은 이름을 다시 조회할 때 대기 시간과 상위 서버의 부하를 줄인다.
- **계층 구조:** 루트, TLD, 권한 있는 서버가 역할을 나눠 전체 이름 공간을 관리한다.

네임 서버의 계층은 대체로 **루트 서버 → 최상위 도메인(TLD) 서버 → 권한 있는 네임 서버** 순서다. 루트 서버는 `.com` 같은 TLD를 담당하는 서버를 알려 준다. TLD 서버는 `example.com`을 담당하는 권한 있는 서버를 알려 준다. 권한 있는 서버는 그 도메인의 최종 레코드 정보를 제공한다. 한 서버가 인터넷의 모든 도메인을 저장하지 않아도 되므로 관리 범위와 쿼리 부하를 분산할 수 있다.

네임 서버의 역할은 다음과 같다.

- **루트 서버:** `.com`, `.edu` 같은 최상위 도메인을 담당하는 서버의 정보를 알려 준다.
- **최상위 도메인(TLD) 서버:** `example.com`처럼 해당 TLD에 속한 도메인의 권한 있는 서버를 알려 준다.
- **권한 있는 네임 서버:** 자신이 담당하는 도메인의 최종 레코드 정보를 제공한다.

리소스 레코드는 이름을 주소에 매핑하는 `A`만 있는 것이 아니다. `NS`를 통해 해당 도메인 정보를 책임지는 서버를 찾고, `CNAME`을 통해 별칭이 가리키는 정식 이름을 따라가며, `MX`로 메일을 받을 서버를 찾는다. 권한 있는 네임 서버는 자신의 도메인에 대해 공식적으로 레코드를 제공하는 위치다. 루트와 TLD 서버가 모든 하위 도메인의 주소를 직접 저장하는 대신 ‘다음에는 어디에 물어야 하는가’를 알려 주므로, 도메인의 수가 늘어도 역할을 나누어 관리할 수 있다.

### 4.1.1 DNS 쿼리

사용자는 보통 **재귀 리졸버**에 “이 이름의 주소를 찾아 달라”고 요청한다. 리졸버에 답이 캐시되어 있으면 바로 반환한다. 없다면 루트, TLD, 권한 있는 서버를 따라가며 답을 얻은 후 사용자에게 돌려준다.

캐시에 없는 `www.example.com`을 조회한다면 흐름은 다음과 같다.

1. 브라우저 또는 운영 체제가 설정된 리졸버에 주소를 요청한다.
2. 리졸버는 루트 서버에서 `.com`을 담당하는 서버의 정보를 얻는다.
3. `.com` 서버에서 `example.com`을 담당하는 권한 있는 서버의 정보를 얻는다.
4. 권한 있는 서버에서 `www.example.com`의 레코드를 확인한다. 별칭이라면 연결된 이름을 더 확인해야 한다.
5. 리졸버가 결과를 사용자에게 돌려주고, 캐시 정책에 따라 결과를 보관한다.

이 순서는 한 번의 사용자 요청이 내부에서는 여러 DNS 질의로 이어질 수 있음을 보여 준다. 이미 캐시된 위임 정보나 최종 주소가 있다면 해당 단계는 생략될 수 있다.

**반복 질의**에서는 질의를 받은 서버가 자신이 아는 답이나 다음에 물어볼 서버를 알려 준다. 질의를 수행하는 쪽은 그 안내를 따라 다음 서버에 다시 묻는다. **재귀 질의**에서는 질의를 받은 서버에 최종 답을 찾아 반환할 책임을 맡긴다. 일반적인 조회 흐름에서는 사용자 측이 재귀 리졸버에 요청하고, 재귀 리졸버가 여러 DNS 서버에 반복 질의를 수행한다. 책의 본문과 옮긴이 노트에는 이 두 용어를 설명하는 방식이 섞여 있으므로, **누가 다음 서버에 다시 묻는가**를 기준으로 구분하는 편이 명확하다.

반복 질의는 ‘답을 얻을 때까지 다음 서버를 차례로 찾아가는 방식’, 재귀 질의를 ‘질의를 받은 쪽이 최종 답을 대신 구해 주는 방식’이다. 옮긴이 노트에는 사용자 컴퓨터가 각 계층에 직접 묻는 비유와 로컬 리졸버가 묻는 설명이 함께 나온다. 실제 흐름을 이해할 때는 **클라이언트가 리졸버에 답을 부탁하는 단계**와 **리졸버가 루트·TLD·권한 서버의 안내를 따라가는 단계**를 나눠 보는 것이 안전하다. 반복 질의는 다음 서버를 알려 주는 응답을 활용하고, 재귀 질의는 질의를 받은 서버가 최종 응답을 마련한다는 차이가 있다.

두 방식을 역할 기준으로 적으면 다음과 같다.

- **반복 질의:** 질의를 수행하는 리졸버가 루트, TLD, 권한 있는 서버에 차례로 묻고 다음에 물어볼 곳을 안내받는다.
- **재귀 질의:** 요청을 받은 리졸버가 최종 답을 구해 요청자에게 돌려준다. 일반적인 사용자 기기는 이 방식으로 설정된 리졸버에 주소를 요청한다.

DNS 캐시는 브라우저, 운영 체제, 로컬 네트워크, 재귀 리졸버 등 여러 위치에 있을 수 있다. 같은 이름을 매번 루트 서버부터 조회하지 않아도 되므로 응답 시간이 줄고 전체 DNS 인프라의 부하도 낮아진다. 대신 변경된 주소가 캐시에서 사라지기 전에는 이전 정보를 받는 사용자가 있을 수 있다.

브라우저, 운영 체제, 사용자 네트워크의 로컬 네임 서버, ISP 리졸버를 캐시 위치로 나열한다. 앞단의 캐시에서 답을 얻으면 뒤쪽 네임 서버는 이번 요청을 처리하지 않아도 된다. 이는 사용자 응답 시간을 줄일 뿐 아니라 네트워크 트래픽과 상위 DNS 인프라에 대한 질의량도 줄인다. 캐시의 이익과 맞바꾸는 것이 변경 전파 시간이다. 레코드를 수정해도 각 캐시가 가진 이전 값은 유효 기간 동안 남아 있을 수 있다.

애플리케이션 설정에 도메인 대신 IP 주소를 직접 넣는 예시에서 IP를 직접 쓰면 그 연결에서 이름 조회를 생략할 수 있지만, 서버 주소가 바뀔 때 설정을 고쳐야 하고 DNS를 통한 주소 분산을 활용하기 어렵다. TLS 인증서가 보통 도메인 이름을 기준으로 검증된다는 점도 고려해야 한다. 따라서 DNS 조회 한 번의 지연만 보지 말고 주소 변경의 유연성과 서비스 진입 경로까지 함께 판단해야 한다.

도메인 이름 사용의 이유는 다음과 같다.

- **유연성:** 서버 IP가 바뀌어도 도메인이 새 주소를 가리키도록 수정하면 애플리케이션 설정을 그대로 사용할 수 있다.
- **로드 밸런싱:** 도메인에 연결된 여러 주소를 이용해 접속 경로를 분산할 수 있다.
- **보안:** TLS 인증서가 도메인 이름을 기준으로 검증되는 경우가 많다.

DNS 캐싱의 효과와 위치는 다음과 같다.

- **효과:** 이미 가진 답을 로컬에서 반환해 조회 시간을 줄이고, 상위 DNS 서버로 향하는 질의와 네트워크 트래픽을 줄인다.
- **캐시 위치:**
  - 사용자의 웹 브라우저.
  - 운영 체제.
  - 사용자 네트워크의 로컬 네임 서버.
  - ISP의 재귀 리졸버.

예를 들어 `api.example.com`을 처음 조회한다고 가정하자. 사용자 기기에 답이 없으면 재귀 리졸버에 묻고, 리졸버에도 없다면 상위 DNS 서버의 안내를 따라 권한 있는 서버까지 찾아간다. 최종 주소를 받으면 리졸버와 사용자 기기의 캐시에 일정 시간 보관한다. 이후 같은 이름을 조회하는 요청은 캐시에서 답할 수 있으므로 전체 조회 과정을 반복하지 않는다.

## 4.2 DNS의 확장성, 신뢰성, 일관성

### 4.2.1 확장성

DNS는 도메인 계층을 여러 조직과 서버에 위임한다. 모든 질의를 중앙 서버 한 곳에서 처리하지 않고, 캐시된 답은 사용자 가까운 곳에서 제공한다. 여러 지역에 서버를 두는 것도 전 세계의 조회량을 처리하는 데 도움이 된다. 이러한 계층 구조와 캐싱 덕분에 사용자와 도메인이 늘어도 부하를 나누어 처리할 수 있다.

예를 들어 새로운 `example.com` 서비스가 추가되어도 루트 서버에 그 서비스의 모든 호스트 레코드를 저장하지 않는다. 상위 계층은 담당 서버를 가리키고, 해당 도메인의 권한 있는 서버가 자기 레코드를 관리한다. 전 세계에 분산된 서버 인스턴스와 계층별 위임을 확장성의 근거로 든다. 반복해서 조회되는 주소는 가까운 캐시에서 처리되어 상위 계층까지 올라가는 질의 수가 줄어든다.

### 4.2.2 신뢰성

서버를 중복 배치하면 한 서버가 응답하지 않아도 다른 서버가 질의를 처리할 수 있다. 캐시는 상위 서버에 일시적인 문제가 있을 때 이미 알고 있는 답을 제공하는 데 도움이 된다. DNS 요청은 응답을 받지 못했을 때 재시도할 수 있으며, 실제 조회의 안정성은 리졸버와 네임 서버의 구성에 달려 있다.

책은 여러 지역의 중복 서버와 여러 단계의 캐시를 신뢰성의 기반으로 설명한다. 한 네임 서버가 응답하지 않아도 다른 서버로 질의할 수 있고, 이미 캐시된 주소라면 상위 서버에 도달하지 않고 답을 얻을 수 있다. DNS 질의에서 흔히 쓰이는 UDP는 전달 성공을 자체적으로 보장하지 않으므로, 응답이 없으면 리졸버가 다시 시도하는 방식도 중요하다. 다만 캐시에 답이 없는 이름이나 캐시가 만료된 이름은 상위 서버 장애의 영향을 받을 수 있다.

### 4.2.3 일관성

DNS 레코드를 변경했다고 모든 사용자가 즉시 새 주소를 받지는 않는다. 캐시된 레코드는 유효 기간인 **TTL** 동안 남을 수 있고, 리졸버마다 캐시가 갱신되는 시점도 다르다. DNS는 이런 전파 지연을 받아들이는 방식으로 조회 성능과 확장성을 얻는다. 따라서 주소 변경이나 지역 전환을 계획할 때는 새 레코드만 준비할 것이 아니라 이전 주소로 들어오는 요청을 전환 기간에 어떻게 처리할지도 결정해야 한다.

TTL은 레코드가 얼마 동안 캐시될 수 있는지 나타내는 값이다. 각 사용자와 리졸버가 다른 시각에 기존 레코드를 받았다면 만료 시점도 달라진다. 따라서 변경 직후에는 어떤 사용자는 새 주소를, 다른 사용자는 이전 주소를 받을 수 있다. 책은 DNS가 실시간으로 모든 캐시를 맞추는 강한 일관성보다 높은 조회 성능을 우선하며, 변경이 점진적으로 퍼지는 최종 일관성의 성격을 가진다고 설명한다. 변경 전파가 끝나는 시간은 캐시와 설정에 따라 달라질 수 있다.

예를 들어 서비스를 새 로드 밸런서로 옮길 때 DNS 주소를 변경해도 일부 사용자는 예전 주소를 계속 사용할 수 있다. 예전 경로를 곧바로 없애면 그 사용자만 접속에 실패한다. 이전 주소를 전환 기간에 유지하거나 새 서비스로 전달할 수 있게 설계해야 한다. TTL은 이런 전환 기간을 추정하는 데 필요한 값이지만, 실제 클라이언트와 캐시의 동작도 관찰해야 한다.

## 4.3 로드 밸런서

로드 밸런서는 들어오는 요청을 여러 서버에 분배한다. 특정 서버에 트래픽이 몰리는 것을 줄이고, 정상 서버만 사용하도록 선택하며, 서버를 추가했을 때 늘어난 처리 능력을 활용한다. 여러 서버가 있더라도 클라이언트가 각각의 서버 주소와 상태를 직접 관리할 필요가 없게 만든다.

책은 로드 밸런싱을 서버뿐 아니라 CPU, 저장 장치, 네트워크 연결 같은 자원에 작업을 나누는 넓은 개념으로 소개한다. 서비스 앞에 놓인 로드 밸런서는 클라이언트 요청을 백엔드 서버 풀로 전달하는 형태가 대표적이다. 한 서버로 모든 요청이 몰리면 그 서버의 자원만 포화되고 다른 서버는 놀 수 있다. 요청을 여러 서버에 분배하면 자원을 고르게 쓰고 전체 처리량을 높일 수 있다. 일부 서버가 느려지거나 실패할 때 다른 서버를 사용하도록 하면 서비스 중단 대신 성능이 점진적으로 낮아지는 형태로 대응할 수도 있다.

책이 열거한 로드 밸런싱의 효과는 다음과 같다.

- 트래픽을 여러 서버로 나누어 특정 서버의 과부하를 막는다.
- 장애가 나거나 느려진 서버를 제외하고 정상 서버로 요청을 돌린다.
- 일부 서버가 중단되어도 나머지 서버가 요청을 처리해 가용성을 유지한다.
- 트래픽이 크게 늘어도 서비스가 갑자기 멈추기보다 응답 속도가 점진적으로 저하되게 한다.
- 서버 풀에 인스턴스를 추가해 수평으로 처리 용량을 늘린다.

### 4.3.1 로드 밸런서 위치

로드 밸런서는 클라이언트와 웹 서버 사이에 둘 수도 있고, 웹 서버와 애플리케이션 서버 사이, 애플리케이션 서버와 데이터 계층 사이에 둘 수도 있다. 이렇게 하면 각 계층을 별도로 확장하고 비정상 인스턴스를 해당 계층에서 제외할 수 있다. 다만 요청이 지나는 계층이 많아질수록 각 계층의 지연 시간과 장애 가능성도 함께 고려해야 한다.

예를 들어 웹 서버만 늘려야 하는 상황이면 클라이언트 진입점에서 여러 웹 서버로 요청을 나눈다. 애플리케이션 서버의 처리량이 부족하다면 웹 서버와 애플리케이션 서버 사이에서 분산한다. 데이터베이스 앞에 배치할 때는 어떤 노드가 읽기 또는 쓰기를 받아도 되는지, 복제본의 상태가 어떤지까지 고려해야 한다. 계층마다 부하와 장애 범위가 다르므로 로드 밸런서가 적용할 헬스 체크와 선택 규칙도 달라진다.

### 4.3.2 로드 밸런서의 장점

책은 단순한 요청 분산에 더해 세 가지 기능을 글머리표로 설명한다.

- **헬스 체크:** 백엔드가 요청을 처리할 수 있는지 확인하고 비정상 서버를 분배 대상에서 제외한다.
- **TLS 종료:** 로드 밸런서가 클라이언트의 TLS 연결을 처리해 인증서 관리와 복호화의 진입점이 된다. 백엔드 구간을 어떻게 보호할지는 별도로 결정한다.
- **트래픽 분석:** 연결 수, 응답 시간, 요청 패턴을 관찰해 서버 자원 활용과 분배 방식을 조정한다.

헬스 체크가 ‘서버가 살아 있음’만 확인할지 ‘실제로 핵심 요청을 처리할 수 있음’까지 확인할지에 따라 장애 감지의 품질이 달라진다. TLS를 로드 밸런서에서 종료하면 백엔드가 복호화를 반복하지 않아도 되지만, 뒤쪽 통신을 평문으로 둘지 다시 암호화할지 정해야 한다. 수집한 연결 수와 응답 시간은 동적 분배에도 활용할 수 있다.

### 4.3.3 전역 로드 밸런싱과 로컬 로드 밸런싱

**전역 로드 밸런싱(GSLB)**은 사용자 요청을 어느 지역 또는 데이터 센터로 보낼지 정한다. 사용자 위치, 지역의 가용 상태, 용량이 판단 기준이 될 수 있다. 지역 전체에 장애가 나면 다른 지역으로 전환하는 역할도 맡을 수 있다. **로컬 로드 밸런싱**은 선택된 지역 안에서 어떤 서버가 요청을 받을지 정한다. 전역 단계와 로컬 단계의 판단 대상이 다르므로 두 계층을 조합할 수 있다.

책의 그림에서는 먼저 GSLB가 여러 데이터 센터 중 목적지를 선택한다. 각 데이터 센터 안에는 로컬 로드 밸런서가 있어서 그 지역의 서버 풀로 요청을 나눈다. 전역 단계는 지리적 거리와 데이터 센터 전체의 상태를 보고, 로컬 단계는 서버 한 대 한 대의 상태와 부하를 본다. 로컬 단계가 지역 서버들의 상태·용량 정보를 전역 단계에 제공하면 GSLB는 트래픽을 받아들일 지역을 선택하는 데 활용할 수 있다. 서버 한 대의 장애와 데이터 센터 전체의 장애를 서로 다른 계층에서 처리하는 구조다.

### 4.3.4 DNS와 전역 로드 밸런서

한 도메인에 여러 주소를 반환하면 DNS도 전역 트래픽을 어느 정도 나눌 수 있다. 예를 들어 여러 데이터 센터의 주소를 차례로 제공하는 방식이다. 그러나 DNS 응답은 캐시되고 클라이언트가 여러 주소 중 어느 것을 사용할지도 DNS가 완전히 통제하지 못한다. 서버가 방금 장애를 일으켰거나 한 지역에 트래픽이 급증한 상황을 즉시 정교하게 반영하기 어렵다. TTL을 짧게 설정하면 변경 전파에 도움을 줄 수 있지만 DNS 질의량이 늘고, 이미 캐시한 클라이언트의 동작까지 곧바로 바뀌지는 않는다.

책은 DNS 라운드 로빈의 한계를 더 구체적으로 설명한다. 한 ISP의 리졸버 뒤에 이용자가 많이 모이면 DNS 응답을 번갈아 주어도 실제 데이터 센터로 가는 요청량은 고르게 나뉘지 않을 수 있다. 응답에 주소가 여러 개 있으면 클라이언트가 어느 주소를 택할지 DNS가 제어하지 못한다. 기본적인 DNS 응답에는 백엔드 서버의 현재 연결 수나 응답 지연도 반영되지 않는다. 지리적 위치를 고려한 응답이나 애니캐스트 같은 기법으로 일부 한계를 보완할 수 있지만 구성이 복잡해진다. 캐시의 TTL 때문에 장애 지역을 목적지에서 제외해도 기존 주소를 계속 쓰는 사용자가 남을 수 있다.

책이 글머리표로 제시한 제약을 구분하면 다음과 같다.

- **응답에 담을 정보의 한계:** 책은 DNS 응답에 모든 서버 주소를 담기 어렵다는 점을 언급한다. 응답 크기 제한은 사용하는 DNS 기능과 전송 방식에 따라 달라진다.
- **클라이언트의 주소 선택:** 여러 주소를 받아도 어느 주소를 실제로 사용할지는 클라이언트 측 동작에 좌우된다.
- **지역과 거리 판단:** 기본적인 DNS 라운드 로빈만으로는 사용자와 가장 가까운 서버를 정확하게 고르기 어렵다. 위치 기반 응답이나 애니캐스트 같은 추가 기법이 필요할 수 있다.
- **장애 전환 속도:** 긴 TTL로 이전 주소가 캐시되면 장애 지역을 제외해도 일부 사용자는 한동안 그 주소로 접속한다.

따라서 DNS 기반의 전역 분산과 데이터 센터 안의 로컬 로드 밸런서를 구분한다. 전자는 큰 범위에서 목적지를 고르고, 후자는 현재 정상인 서버를 세밀하게 선택한다.

클라이언트는 지역의 가상 IP 주소에 연결하고, 로컬 로드 밸런서는 그 시점에 사용 가능한 백엔드 서버로 요청을 전달하는 식이다. DNS만으로 모든 서버의 상태를 실시간으로 반영하려는 것보다, 지역을 고른 뒤 지역 내부의 세밀한 분산을 별도 계층에 맡기는 편이 책에서 제시한 구조에 가깝다.

서울과 싱가포르에 데이터 센터가 있고 각 지역에 애플리케이션 서버가 여러 대 있다고 가정하자. 전역 분산 계층은 사용자를 어느 데이터 센터로 보낼지 결정한다. 서울 지역을 선택한 뒤에는 서울의 로컬 로드 밸런서가 정상인 서버 한 대를 고른다. 서울 서버 한 대의 장애는 로컬 단계에서 처리할 수 있지만, 서울 지역 전체의 장애는 전역 단계의 전환이 필요하다. 이렇게 **장애의 범위에 따라 결정을 내리는 계층**이 달라진다.

### 4.3.5 로드 밸런서가 사용하는 알고리즘

책은 서버 선택 알고리즘을 다음처럼 글머리표로 나눈다.

- **라운드 로빈:** 서버 목록을 순서대로 돌며 요청을 배정한다. 단순하지만 서버 성능과 현재 부하는 반영하지 않는다.
- **가중치 기반 라운드 로빈:** 서버 용량에 맞춰 가중치를 주고 처리 능력이 높은 서버에 더 많은 요청을 보낸다.
- **최소 연결:** 현재 연결 수가 가장 적은 서버를 고른다. 오래 유지되는 연결이 섞여 있을 때 유용하지만 연결 상태를 추적해야 한다.
- **최소 응답 시간:** 응답 속도가 빠른 서버에 요청을 보낸다. 최근 측정값의 변동성을 고려해야 한다.
- **IP·URL·일관된 해싱:** 클라이언트 IP나 요청 URL 같은 키를 해싱해 목적지를 정한다. 같은 키의 요청을 일정하게 배치할 수 있지만 키별 부하가 다르면 쏠릴 수 있다.

라운드 로빈에서 서버가 `A`, `B`, `C`라면 요청을 `A → B → C → A` 순서로 보낸다. 세 서버의 성능과 요청 처리 시간이 비슷할 때는 간단하지만, 한 요청이 아주 오래 걸리거나 `C`의 처리 능력이 낮으면 실제 부하가 같아지지 않는다. 가중치 기반 라운드 로빈은 서버별 용량 차이를 미리 설정한 비율로 반영한다. 최소 연결은 진행 중인 연결 수를 관찰하므로 오래 유지되는 연결이 섞여 있을 때 유용하다. 최소 응답 시간은 최근 응답 속도를 사용하지만, 측정값이 순간적인 변동에 흔들릴 수 있다.

해시 기반 방식은 요청의 특정 키를 목적지 결정에 사용한다. 클라이언트 IP를 키로 쓰면 같은 IP의 요청이 같은 서버로 가기 쉽고, URL을 키로 쓰면 같은 경로의 요청을 일정하게 배치할 수 있다. 그러나 한 IP에 많은 사용자가 모이거나 특정 URL에 요청이 집중되면 균등 분산과 충돌한다. 서버가 추가되거나 제거될 때 해시 매핑이 크게 바뀌지 않도록 3장에서 다룬 일관된 해싱을 사용할 수 있다. **요청을 고르게 나누는 목표와 같은 키를 같은 서버로 보내는 목표**를 함께 고려해야 한다.

서버 상태를 거의 보지 않고 미리 정한 규칙에 따라 보내는 방식을 **정적 분배**, 현재 부하나 응답 속도에 맞춰 선택을 바꾸는 방식을 **동적 분배**로 이해할 수 있다. 동적 분배는 변화에 적응하지만 상태 수집과 판단에 비용이 든다.

책의 구분에서 정적 알고리즘은 실시간 부하를 추적하지 않으므로 구성이 단순하다. 서버 수가 적고 처리 능력이 비슷한 환경에서는 이 단순성이 유리할 수 있다. 동적 알고리즘은 현재 또는 최근의 연결 수, 응답 시간, 서버 상태를 반영한다. 특정 서버가 느려졌거나 빠졌을 때 대응하기 좋지만, 그 상태를 지속해서 수집하고 여러 로드 밸런서가 필요한 정보를 공유해야 할 수 있다. **더 정교한 선택은 더 많은 관찰과 관리 비용을 요구한다.**

책은 세션 연결 정보를 기억하는 **스테이트풀** 방식과 저장된 세션 상태 없이 요청을 배정하는 **스테이트리스** 방식도 비교한다. 전자는 같은 사용자를 특정 백엔드에 계속 연결해야 하는 경우에 쓸 수 있지만 상태의 공유와 복구가 필요하다. 후자는 로드 밸런서 자체를 늘리기 쉽지만 서버 변경 시 기존 세션의 목적지가 달라질 수 있다. 세션을 백엔드 한 대에만 저장하지 않는 구조라면 이런 제약을 줄일 수 있다.

책의 택배 기사 비유는 두 방식을 다음과 같이 비교한다.

- **스테이트풀:** 고객에게 담당 기사를 지정하고 다음 배송도 같은 기사에게 맡긴다. 실제 로드 밸런서에서는 연결이나 세션 정보를 기억해 같은 백엔드로 보내는 방식에 해당한다. 담당 서버가 빠지거나 로드 밸런서를 늘릴 때 배정 정보를 공유·복구해야 한다.
- **스테이트리스:** 요청이 올 때마다 규칙으로 목적지를 다시 정한다. 유지할 세션 상태가 적어 확장하기 쉽지만 서버 구성이 변하면 같은 고객의 목적지가 달라질 수 있다.

책은 안정성, 확장성, 복잡성의 균형에 따라 두 방식을 섞을 수 있다고 설명한다.

### 4.3.6 OSI 모델의 각 계층에서 로드 밸런싱

**4계층(L4)** 로드 밸런서는 주로 IP·포트와 TCP/UDP 연결 정보를 보고 목적지를 정한다. 요청의 애플리케이션 내용을 깊게 해석하지 않으므로 비교적 단순하고 빠르게 분배할 수 있다. **7계층(L7)** 로드 밸런서는 HTTP의 호스트, 경로, 헤더, 쿠키 등을 보고 서비스나 인스턴스를 선택한다. 경로별 라우팅, 헤더 수정, 속도 제한 같은 기능을 구성할 수 있지만 요청 내용을 처리하는 비용이 따른다. 필요한 라우팅 정밀도와 프로토콜에 따라 한 방식 또는 두 방식을 조합한다.

책은 OSI 모델의 전송 계층과 응용 계층을 기준으로 두 방식을 구분한다. L4에서 같은 TCP 연결의 패킷은 같은 백엔드로 이어져야 한다. TCP와 UDP의 연결 특성이 다르므로 분배 방식도 그에 맞춰야 한다. L7은 HTTP 요청의 경로가 `/images`인지 `/api`인지, 특정 헤더나 쿠키가 있는지 등을 읽고 다른 백엔드로 보낼 수 있다. 이런 조건 기반 라우팅을 하려면 애플리케이션 프로토콜을 이해하고 경우에 따라 TLS를 종료해야 한다. L4가 기본 트래픽 분배를 맡고 L7이 세부 라우팅을 맡는 배치도 가능하다.

### 4.3.7 로드 밸런서의 배치

책은 DNS, 라우터, L4 로드 밸런서, L7 로드 밸런서를 이어 놓은 다층 배치도 소개한다. 바깥쪽 계층은 큰 단위의 트래픽을 나누고, 안쪽 계층은 요청 내용과 서버 상태를 더 세밀하게 반영한다. 이런 배치는 대규모 시스템의 한 예이지 모든 서비스가 네 단계를 전부 필요로 한다는 뜻은 아니다. 계층을 추가할 때는 그 계층이 해결하는 병목이나 장애 상황을 분명히 해야 한다.

책의 네 단계 배치는 다음과 같다.

- **0단계, DNS:** 서비스 이름에 대해 여러 진입 주소 중 하나 또는 여럿을 제공한다.
- **1단계, 라우터:** 주소와 네트워크 규칙, 순환 분배 같은 기준으로 들어오는 트래픽을 나눈다.
- **2단계, L4 로드 밸런서:** 연결 단위로 다음 처리 지점에 트래픽을 분배하고 같은 연결의 흐름을 유지한다.
- **3단계, L7 로드 밸런서:** HTTP 요청 내용과 개별 서버의 건강 상태를 보고 최종 백엔드를 고른다.

각 단계가 다루는 정보의 수준이 다르다. 바깥쪽은 큰 범위의 목적지를 정하고, 안쪽으로 갈수록 요청의 구체적인 내용과 개별 서버의 상태를 활용한다. 여러 계층을 두면 부하와 장애를 나눠 다룰 수 있지만 각 계층 자체의 용량과 장애 전환도 고려해야 한다.

### 4.3.8 로드 밸런서의 구현

- **하드웨어 장비:** 전용 장비로 높은 처리량을 제공할 수 있지만 구매·유지 비용과 설정 부담이 있다.
- **소프트웨어:** 일반 서버에서 실행하며 규칙을 유연하게 바꿀 수 있다. 확장과 운영은 사용자가 설계해야 한다.
- **클라우드 관리형 서비스:** 클라우드 제공 업체가 장비와 기본 운영을 맡는다. 사용 편의성과 확장성이 장점이며 비용 모델과 제공 기능의 범위를 확인해야 한다.

책은 하드웨어 장비가 높은 동시 처리량을 제공하지만 구매비, 설정·유지 보수 비용, 벤더 종속, 장비 이중화 비용이 뒤따른다고 설명한다. 소프트웨어 방식은 일반 서버에서 규칙을 유연하게 바꾸고 자동화를 붙이기 쉽지만, 운영자가 배포와 용량, 장애 대응을 맡는다. LBaaS는 제공 업체가 기반 인프라를 관리하며 사용량이나 계약 조건에 따라 비용을 지불하는 방식이다. 지역 안의 분산뿐 아니라 전역 트래픽 관리 기능을 제공할 수도 있다. 매우 높은 처리량이 필요한 장비와 유연한 소프트웨어·관리형 서비스를 함께 사용하는 하이브리드 구성도 책에서 언급한다.

구현 형태를 고를 때는 처리량뿐 아니라 장애 시 대체 경로, 설정 관리, 운영 인력, 비용을 함께 비교한다.

## 4.4 애플리케이션 게이트웨이

애플리케이션 게이트웨이는 클라이언트와 백엔드 서비스 사이에서 **애플리케이션 요청을 이해하고 공통 정책을 적용하는 진입점**이다. 로드 밸런서처럼 요청을 전달하지만, 어느 서비스로 보낼지 판단하는 기준과 적용하는 정책이 더 넓다. API 게이트웨이라는 이름으로 제공되는 제품도 있다.

책의 그림은 클라이언트가 여러 서비스를 직접 호출하지 않고 게이트웨이를 먼저 거치는 구조다. 게이트웨이는 들어온 요청을 검사하고 적절한 서비스에 전달하며, 응답을 다시 클라이언트에 돌려준다. 요청의 경로만 정하는 데 그치지 않고 인증과 권한, 보안 검사, 캐싱, 관측처럼 여러 서비스에 공통으로 필요한 처리도 맡는다. L7 로드 밸런서와 기능이 겹칠 수 있으므로 실제 설계에서는 제품 이름보다 **어떤 정책을 어느 진입점에서 실행하는지**를 분명히 하는 것이 중요하다.

### 4.4.1 애플리케이션 게이트웨이의 기능과 역할

- **고급 요청 라우팅:** 호스트 이름, 경로, 헤더, 요청을 보낸 IP 주소 등을 조건으로 적합한 백엔드 서비스에 연결한다.
- **보안:** 인증, 접근 제어, TLS 종료, DDoS 방어, 웹 애플리케이션 방화벽(WAF) 연계 같은 공통 정책을 입구에서 적용한다.
- **가속화와 오프로딩:** 캐싱, 압축, TCP 연결 관리, TLS 처리를 맡아 백엔드가 직접 수행할 작업을 줄인다.
- **모니터링:** 요청 로그, 메트릭, 트레이스를 중앙에서 모아 어떤 요청이 어디에서 실패하거나 느려지는지 확인한다.
- **적응성:** 요청·응답의 형식이나 프로토콜을 조정해 클라이언트와 변경된 백엔드 또는 기존 서비스를 연결한다.

고급 라우팅에서는 `/orders`와 `/products` 같은 경로뿐 아니라 호스트 이름, 특정 헤더, 요청을 보낸 IP 주소를 조건으로 사용할 수 있다. 보안 기능으로는 인증과 접근 제어, TLS 종료, DDoS 방어, WAF 연계가 나온다. 이 정책을 게이트웨이에 모으면 여러 백엔드가 같은 기준을 적용받을 수 있다. 다만 각 서비스가 자신의 데이터에 대한 최종 권한 검사를 더 해야 하는 경우까지 모두 게이트웨이에 맡겨서는 안 된다.

성능 측면에서는 반복 응답을 캐시하거나 데이터를 압축하고, TCP 연결과 TLS 처리의 일부를 게이트웨이에서 맡을 수 있다. 이렇게 하면 백엔드 서버의 CPU와 연결 관리 부담을 줄일 수 있지만 게이트웨이의 자원 사용은 늘어난다. 중앙에서 요청 로그, 메트릭, 트레이스를 모으면 어느 경로가 느리고 어떤 서비스에서 오류가 발생했는지 파악하기 쉬워진다. 요청·응답 변환은 기존 서비스와 새 클라이언트의 프로토콜이나 데이터 형식이 다를 때 연결에 도움이 된다. 책은 이 기능을 변화하는 백엔드에 적응하는 능력으로 설명한다.

이 기능들을 한곳에 모으면 서비스마다 같은 코드를 반복하지 않아도 된다. 반면에 게이트웨이 자체가 과부하나 장애의 집중 지점이 되지 않도록 용량과 중복 구성을 설계해야 한다. L7 로드 밸런서와 기능이 겹칠 수 있으므로 이름보다 **실제로 어느 장치가 어떤 정책을 적용하는지**가 중요하다.

## 4.5 마이크로서비스 아키텍처

마이크로서비스는 큰 애플리케이션을 기능별로 나누어 각 서비스를 독립적으로 개발·배포·확장할 수 있게 한다. 대신 클라이언트가 서비스마다 다른 주소와 API를 직접 알아야 한다면 백엔드 구조의 변경이 곧 클라이언트 변경으로 이어진다. 인증, 접근 제어, 모니터링 같은 공통 기능도 서비스마다 중복될 수 있다.

책은 서비스가 REST/HTTP 같은 비교적 가벼운 프로토콜과 명확한 인터페이스로 통신한다고 설명한다. 주문, 상품, 사용자 서비스가 각각 따로 배포되면 팀이 각 부분을 독립적으로 변경하고 필요한 부분만 확장할 수 있다. 그러나 인스턴스가 동적으로 늘고 줄어들면 클라이언트가 모든 주소를 고정해 두기는 어렵다. 여러 서비스를 하나의 제품처럼 보이게 하는 API의 일관성도 과제가 된다.

게이트웨이는 여러 서비스를 **하나의 논리적 API** 뒤에 두고, 서비스 디스커버리와 동적 라우팅으로 현재 살아 있는 인스턴스를 찾는다. 공통 보안과 관측 정책을 적용하면 각 서비스는 자신의 비즈니스 기능에 집중할 수 있다. 그러나 모든 업무 로직을 게이트웨이에 쌓으면 서비스 분리의 장점이 줄어든다. 공통 진입 정책과 각 서비스의 고유한 책임을 구분해야 한다.

책이 글머리표로 제시한 마이크로서비스 환경에서의 역할은 다음과 같다.

- 여러 서비스를 하나의 논리적인 API로 묶어 클라이언트에 제공한다.
- 서비스 디스커버리와 동적 라우팅으로 현재 동작하는 백엔드 인스턴스에 요청을 전달하고, 인스턴스 간 부하를 분산한다.
- 보안, 모니터링, 안정성처럼 여러 서비스에 공통으로 필요한 기능을 진입점에서 처리한다.
- 백엔드와 별도로 게이트웨이의 새 버전을 배포할 수 있다.
- 서비스별 독립적인 개발과 확장을 지원한다.

이 구조 덕분에 백엔드를 나누면서도 클라이언트가 내부 구성 변경을 모두 알 필요가 없어진다.

예를 들어 클라이언트가 `/orders/123`을 요청하면 게이트웨이는 인증을 확인하고 주문 서비스로 요청을 보낼 수 있다. `/products/456`은 상품 서비스로 보낸다. 클라이언트에는 일관된 진입 주소를 제공하면서도 뒤의 서비스는 독립적으로 배포할 수 있다. 이때 주문의 실제 비즈니스 규칙은 주문 서비스가 소유하고, 게이트웨이는 공통 진입 정책과 라우팅을 담당한다.

<br>

## 4.6 클라우드 네이티브 애플리케이션 게이트웨이 서비스 개요

책은 클라우드 제공 업체의 관리형 API 게이트웨이와 애플리케이션 로드 밸런서, 보안·CDN 서비스를 관련 구성 요소로 소개한다. AWS의 API 게이트웨이·애플리케이션 로드 밸런서, Azure의 애플리케이션 게이트웨이, 구글 클라우드의 보안·CDN 서비스가 사례다. 쿠버네티스 환경에서는 인그레스와 프록시, 서비스 메시 관련 소프트웨어를 조합해 외부 요청의 진입 경로를 만든다.

책에 나온 제품별 예시도 글머리표로 정리하면 다음과 같다.

- **AWS:** API Gateway는 API 생성·배포·관리·보안을, Application Load Balancer는 애플리케이션 요청 라우팅을 맡는 사례로 나온다.
- **Azure:** Application Gateway가 응용 계층 분산과 WAF, TLS 처리, 자동 확장 기능을 제공하는 사례로 나온다.
- **Google Cloud:** Cloud Armor는 보안 정책과 DDoS 대응, Cloud CDN은 캐싱과 콘텐츠 전송 성능을 담당하는 사례로 나온다.
- **Kubernetes:** Istio, Kong, Traefik, Ambassador 등이 외부 트래픽 진입과 프록시·게이트웨이 역할을 하는 도구로 언급된다.

이 목록은 책에 제시된 구성 요소의 예시다. 제품 간 기능 범위가 동일하다는 뜻은 아니며, 실제 구성에서는 라우팅·보안·캐싱을 한 제품에서 처리할지 여러 서비스를 조합할지 결정해야 한다.

관리형 서비스는 인프라 운영 부담을 줄일 수 있지만, 각 서비스가 담당하는 범위가 같지는 않다. 제품을 고를 때는 필요한 라우팅 조건, 인증과 보안 정책, TLS 처리 위치, 관측 기능, 클라우드 내부 서비스와의 연동, 비용을 확인해야 한다.

## 4.7 온프레미스 옵션

자체 데이터 센터에서도 게이트웨이와 프록시를 운영할 수 있다. 책이 예로 든 소프트웨어는 다음과 같다.

- **Kong:** Kong Gateway와 Kong Mesh를 통해 API 게이트웨이·서비스 메시 기능을 구성한다. 플러그인으로 인증, 보안, 분석 기능을 더할 수 있다.
- **Tyk:** 접근 제어, 개발자 포털, API 기반 설정 기능을 갖춘 게이트웨이의 예다.
- **NGINX:** 프록시와 로드 밸런서로 배치할 수 있으며 속도 제한과 접근 제어를 구성할 수 있다.
- **HAProxy:** 경량 프록시와 부하 분산에 중점을 두고 응용 계층의 요청도 처리하도록 구성할 수 있다.

이 소프트웨어들은 범용 장비에서 실행되므로 자체 데이터 센터에서도 요구에 맞춘 진입 계층을 만들 수 있다. 제품마다 중점과 제공 방식은 다르다.

온프레미스에서는 설정을 직접 제어하고 기존 네트워크에 맞게 구성할 수 있다. 그만큼 배포, 확장, 인증서 관리, 모니터링, 장애 전환을 운영 주체가 책임진다. 클라우드와 온프레미스의 차이는 게이트웨이가 필요한지 여부가 아니라 **누가 인프라를 운영하고 어느 범위까지 직접 제어할지**에 있다.

## 4.8 요약

DNS는 도메인 이름에서 서비스 진입 주소를 찾게 하고, 계층적 위임과 캐싱으로 큰 조회량을 처리한다. 전역 로드 밸런싱은 어느 지역으로 갈지 결정하고 로컬 로드 밸런싱은 그 지역의 정상 서버로 요청을 나눈다. 애플리케이션 게이트웨이는 HTTP 요청의 내용과 공통 정책을 살펴 적합한 서비스에 전달한다. 한 요청이 이동하는 동안 **주소 찾기 → 지역·서버 선택 → 애플리케이션 정책과 라우팅**이 차례로 적용될 수 있다.

각 요소는 장애와 확장 문제도 함께 안는다. DNS 주소 변경은 TTL 때문에 즉시 모든 사용자에게 전달되지 않는다. 로드 밸런서는 백엔드 상태를 관찰해야 하고 자신도 충분한 용량과 중복 구성이 필요하다. 게이트웨이에 공통 기능을 모으면 서비스 개발은 단순해지지만 그 진입점의 과부하와 장애에 대비해야 한다. 책은 이 세 구성 요소를 따로 암기하기보다, 실제 요청이 서비스에 도달하는 과정에서 각각 어떤 결정을 내리는지 연결해서 이해하도록 한다.
