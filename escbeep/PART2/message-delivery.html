지금 확인할 점

ACK(처리 확인 응답): 소비자가 큐에 “이 메시지를 더 전달하지 않아도 된다”고 알리는 응답이다. 실제 업무 완료 여부는 ACK 시점에 따라 다를 수 있다. 이 화면의 세 방식은 보장 수준의 차이를 설명하기 위한 구현 예시다.

정확히 한 번인데 왜 메시지를 두 번 받는가?

수신 횟수와 업무 결과의 반영 횟수를 따로 보아야 한다. ③에서 소비자는 이미 100점을 적립했지만 ACK를 보내기 전에 중단된다. 큐는 처리 완료를 확인하지 못했으므로 M1을 다시 전달한다.

  1. 같은 논리적 메시지는 같은 ID를 사용한다. 재전달된 메시지도 M1이다. 별개의 적립 요청에는 새로운 ID를 부여한다.
  2. M1 처리 기록과 포인트 갱신을 하나의 트랜잭션으로 커밋한다. 두 변경이 모두 저장되거나 모두 취소되어야 한다. 중복 요청이 동시에 들어와도 한 트랜잭션만 성공하도록 M1에 고유 제약을 둔다.
  3. 소비자가 다시 시작해도 DB의 처리 기록은 남는다. M1이 다시 도착하면 기존 기록을 확인하고 추가 적립을 건너뛴 뒤 ACK를 보낸다.

최소 한 번 전달 + 같은 ID의 중복 반영 방지 + 원자적 저장
→ 이 예시의 DB에서는 결과를 한 번만 반영

이처럼 같은 요청을 반복해도 추가 효과가 발생하지 않는 성질을 멱등성이라고 한다. 처리 기록만 먼저 저장하면 적립이 누락될 수 있고, 적립만 먼저 저장하면 재시도 때 중복 적립될 수 있다. 그래서 두 변경을 함께 저장한다. AWS: 멱등한 API와 원자적 처리

보장 범위: 여기서는 같은 DB에 저장하는 포인트와 M1 기록을 다룬다. 별도 결제 API 호출이나 이메일 발송까지 이 트랜잭션으로 보장되지는 않는다. 재전달이 가능한 동안 처리 기록을 유지해야 한다. Kafka의 정확히 한 번 처리 역시 트랜잭션에 포함되는 데이터와 외부 저장소의 연동 방식을 확인해야 한다. Kafka: 메시지 전달 보장과 적용 범위

정상 처리만 보면 세 방식의 결과가 모두 100점이다. 업무 반영 전 장애는 누락 가능성을, 업무 반영 후 확인 전 장애는 중복 가능성을 드러낸다. 강한 보장을 구현하려면 재시도뿐 아니라 처리 기록의 저장·조회와 트랜잭션 등 추가 작업도 필요하다.

언제 사용할까? 세 방식의 사용 사례와 장단점

먼저 메시지가 빠져도 되는지, 같은 업무가 반복돼도 되는지를 판단한다. 다음 사례는 책의 전달 보장 개념과 보충 자료를 바탕으로 구성한 적용 예시다.

① 최대 한 번: 일부 누락을 허용할 수 있을 때

사용 상황: 개별 메시지를 모두 처리하는 것보다 전달 비용을 줄이는 것이 중요하고, 일부 메시지가 빠져도 서비스 목적을 달성할 수 있을 때 선택한다.

예시: 현재 온도를 매초 갱신하는 화면에서 중간 측정값 하나가 빠져도 다음 값으로 갱신할 수 있는 경우다. 모든 측정값을 보존해야 하는 기록 시스템이라면 같은 기준을 적용할 수 없다.

장점

  • 실패한 메시지를 재전달하지 않으므로 재시도에 드는 통신과 처리 비용을 줄일 수 있다.
  • 이 전달 구간의 재전달로 생기는 중복을 다루지 않아도 되므로 처리 구조를 단순하게 만들 수 있다.

단점

  • 소비자가 처리 전에 중단되면 해당 업무가 누락될 수 있다. 위 시연의 ②처럼 ACK를 먼저 보냈다면 큐가 다시 처리할 기회를 주지 않는다.
  • “중복되지 않는다”는 조건만 충족하므로 반드시 완료해야 하는 적립이나 주문 처리에는 이것만으로 충분하지 않다.

② 최소 한 번: 누락을 막고, 중복은 다룰 수 있을 때

사용 상황: 일시적인 장애가 발생해도 작업을 다시 시도해야 하고, 소비자가 중복 요청을 허용하거나 멱등하게 처리할 수 있을 때 선택한다.

예시: 같은 문서 ID와 버전의 데이터를 검색 인덱스에 반영하는 작업이다. 같은 데이터를 다시 써도 최종 결과가 같도록 구성할 수 있다. 서로 다른 버전이 역순으로 도착하는 문제는 별도로 처리해야 한다.

장점

  • 처리 완료가 확인되지 않은 메시지를 다시 전달하므로 일시적인 소비자 장애 후에도 작업을 이어 갈 수 있다.
  • 같은 요청을 반복해도 결과가 달라지지 않는 작업에 적용하면 재시도를 활용하면서도 중복으로 인한 업무 영향을 줄일 수 있다.

단점

  • 업무 반영 후 ACK 전에 중단되면 같은 메시지를 다시 실행할 수 있다. 위 시연의 ③처럼 매번 100점을 더하면 200점이 된다.
  • 재시도에 따른 부하와 지연이 생길 수 있다. 중복이 해로운 업무에서는 요청 ID 관리, 중복 확인, 멱등성 구현 등이 추가로 필요하다.

③ 정확히 한 번: 누락과 중복 반영을 모두 막아야 할 때

사용 상황: 같은 논리적 요청의 결과를 반드시 한 번만 반영해야 하며, 그 결과와 처리 기록을 일관되게 저장할 수 있는 범위에서 선택한다.

예시: 이 화면의 포인트 적립처럼 누락되면 받을 포인트를 받지 못하고, 중복되면 포인트를 더 받는 업무다. 적립 내역과 요청 ID를 같은 DB 트랜잭션에 포함해 한 요청이 한 번만 반영되도록 만든다.

장점

  • 장애 복구와 재전달이 발생해도 정해진 범위 안에서 중복 효과와 누락을 막아 업무 결과의 일관성을 유지할 수 있다.
  • 처리 여부가 불확실한 요청을 재시도하면서도 같은 요청의 결과를 추가로 반영하지 않을 수 있다.

단점

  • 이 예시에서는 처리 기록의 조회·저장, 고유 제약, 트랜잭션이 필요하다. 저장 공간과 실행 비용이 늘고, 동시 처리와 기록 보관 기간도 설계해야 한다.
  • 보장 범위를 넘는 외부 작업까지 자동으로 보호하지는 않는다. 예를 들어 DB 적립과 외부 알림 발송을 함께 보장하려면 외부 시스템과의 연동도 별도로 설계해야 한다.

선택 기준

  1. 일부 누락을 허용할 수 있다면: 최대 한 번으로 처리 비용과 구현 복잡도를 줄일 수 있는지 검토한다.
  2. 누락은 막아야 하고 중복을 다룰 수 있다면: 최소 한 번 전달과 소비자의 멱등한 처리를 함께 검토한다.
  3. 최종 결과의 누락과 중복을 모두 막아야 한다면: 정확히 한 번 반영할 업무 범위와 이를 보장할 저장·트랜잭션 방식을 정한다.

전달 방식과 업무 결과는 구분한다. 최소 한 번 전달을 사용하면서도, 이 시연처럼 중복 방지와 원자적 저장을 결합해 특정 DB 안의 결과를 정확히 한 번 반영할 수 있다. 어떤 방식을 선택했는지와 함께 어디까지 보장하는지를 설명해야 한다.

전달 보장과 외부 저장소의 경계는 Kafka의 메시지 전달 보장 설명을, 재시도의 장점과 멱등성 구현에 필요한 추가 작업은 AWS의 멱등한 API 설계 설명을 참고했다. 실제 성능 차이는 구현과 설정에 따라 달라진다.

책의 설명, 보충 자료, 시연의 가정
  • 책: 『요즘 개발자를 위한 시스템 설계 수업』 7.2.1~7.2.2, PDF 309·312~313쪽. 책은 서비스 품질과 신뢰성을 설계할 때 최대 한 번·최소 한 번·정확히 한 번 가운데 필요한 전달 보장을 정하고, 손실·중복·지연 시간을 고려하도록 설명한다.
  • 설명을 위한 추가 예시: M1의 포인트 적립, 소비자의 중단 시점, ACK 순서, DB의 중복 방지 처리는 책의 원문 예시가 아니다. 세 수준의 차이를 구체적으로 확인하도록 구성했다. 특정 제품의 설정 화면을 재현한 것은 아니다.
  • 보충 자료: KafkaConsumer의 Manual Offset Control / Storing Offsets Outside Kafka에서는 처리와 위치 저장의 순서, 결과와 위치를 함께 저장하는 방법을 설명한다. Kafka의 오프셋 커밋을 여기서 사용하는 일반적인 큐의 ACK와 동일한 API로 취급하지는 않는다.
  • 시연의 조건: 큐에 저장된 M1과 커밋된 DB 데이터는 소비자 장애 후에도 남는다. 소비자는 복구되며, ACK가 없는 메시지는 다시 전달된다. 잘못된 메시지, 재시도 횟수 제한, 영구적인 저장소 장애는 다루지 않는다.
  • 비교 범위: 큐에 안전하게 저장된 메시지를 소비자가 처리하는 구간이다. 생성자에서 큐까지 전달하는 중에 발생하는 손실·중복은 별도로 설계해야 한다. 세 카드는 서로 독립된 실행이므로 한 카드의 ACK가 다른 카드에 영향을 주지 않는다.
