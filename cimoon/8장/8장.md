## 8.2 REST API

### 1. REST API
- 정의: REST(REpresentational State Transfer): 네트워크 애플리케이션 설게하는 아키텍처 스타일
- 많이 사용하는 이유: 표준 HTTP 메서드를 활용, 구조 단순하고 직관적

### 2. 핵심 설계 원칙
- Resource 기반 설계
    - Resource: 객체, 데이터, 서비스 등 client가 접근할 수 있는 요소들, URI로 식별함
- 표준 HTTP 메서드 활용
    - Resource 처리 시 표준 HTTP 메서드(`GET`, `POST`, `PUT`, `DELETE`) 활용
- **Statelessness** (핵심)
    - Client는 요청을 처리하는데 필요한 모든 정보를 요청 안에 직접 포함해야 함.
    - 서버가 이전 요청의 상태를 기억할 필요가 없으므로 시스템 동작이 더욱 안정적, 예측 가능해짐.

### 3. Pros & Cons
- Pros:
    - 구조가 간단하고 익숙한 HTTP 메서드, 상태 코드
    - 간편한 테스트: `cURL`, `Postman`같은 도구 활용 가능
- Cons:
    - 비효율성: 여러 요청 묶어서 한번에 처리해야 하는 복잡한 작업에는 비효율적
    - JSON 포맷의 단점: 데이터양이 많아질 경우 전송되는 페이로드 크기가 커짐.

## 8.3 gRPC

### 1. gRPC
- 정의: gRPC(Google Remote Procedure Call) - RPC(원격 프로시저 호출)를 실행하는 고성능 오픈소스 프레임워크
    - RPC의 정의: 다른 컴퓨터에 있는 함수를 마치 내 프로그램 내의 함수처럼 호출할 수 있도록 해주는 통신 방식
        - Remote: 원격, 즉 다른 컴퓨터에 있는
        - Procedure: 함수/프로시저
        - Call: 호출
        - 예시: 쇼핑몰 서버에서 결제 서버의 결제 기능을 실행하려고 한다. RPC가 없다면 결제 서버와 통신을 해야 한다.

          RPC 사용하면 쇼핑몰 서버에서 `paymentService.pay(orderID)`와 같이 함수 호출처럼 타 서버와 통신할 수 있는 것이다.

          "프레임워크"가 네트워크 통신, 데이터 변환, 원격 함수 실행과 결과를 전달해주는 것이다.
    - 동작 방식:

        1. Client에서 `paymentService.pay(orderID)` 호출
        2. Stub / RPC Runtime: 인자를 Serialize하고 요청 메시지를 생성한다

           **Stub**: 원격 함수를 호출하는 것처럼 사용할 수 있도록 제공되는 대리 코드

           **Serialization**: 함수 인자 같은 데이터를 네트워크로 보낼 수 있는 형태로 변환하는 것.
        3. Network: 요청 메시지를 서버로 전달한다
        4. Server에서 요청을 De-Serialize하고 실제 `paymentService.pay(orderID)` 실행, 결과 반환
        5. Client에서 결과를 받아 사용한다.
    - REST와 차이점은?

      서로 배타적인 기술은 아님, gRPC가 대표적인 예시.

      RPC도 HTTP를 전송 계층으로 사용할 수 있음.
        - 중심 개념: 리소스 ↔ 함수/작업
        - 호출 예시: `POST /payments` ↔ `CreatePayment(Request)`
        - 인터페이스: URL, HTTP method, data ↔ 서비스, 메서드, 인자, 반환값
        - 데이터형식: JSON ↔ 구현에 따라 다름(Protocol Buffers, JSON etc)
- 기반 기술: 구글 개발, HTTP/2 프로토콜 기반 동작
- 설계 특징: 데이터 중심 REST에서 함수 중심으로 설계되어 고효율 API 구현

### 2. 핵심 설계 원칙

- Protocol Buffers (Protobuf) 사용: 인터페이스 정의 언어(IDL)로 프로토콜 버퍼를 사용함.
    - Protobuf란?: 언어/플랫폼에 구애받지 않고 정형 데이터를 직렬화하는 포맷
    - JSON보다 효율적이고 전송 속도가 빠름.
- Stub 자동 생성:
    - `.proto` 파일에 서비스를 정의할 경우, Client/Server를 위한 다양한 스텁을 자동 생성할 수 있음.
    - API 생성 및 관리가 쉬움. 서비스 정의가 변해도 Client/Server 코드에 쉽게 반영 가능
- 풍부한 기능 및 다국어 지원을 한다네요..
    - 제공 기능: 인증, **로드 밸런싱**, **양방향 스트리밍** 오오..

### 3. 주요 활용 사례
- MSA (Micro-Service Architecture): 서비스 간 빠르고 빈번한 고성능 통신이 필요할 때
- 실시간 application: 프로토콜 버퍼 사용해서 메시지 크기가 작고 양방향 스트리밍을 지원하기 때문

### 4. Pros & Cons
- Pros:
    - 페이로드 크기, 통신 속도 REST API에 비해 압도적 월등
    - 프로토콜 버퍼 통해 명확하고 엄격한 데이터 구조 정의 가능
- Cons:
    - 설정/디버깅 복잡성: 바이너리 포맷과 HTTP/2 사용하기 때문
    - 수정에 대한 비용 높음: 통신 방식 변경할 때마다 데이터 구조 다시 정의하고 코드로 컴파일해서 배포해야 하기 때문

## 8.3 비교
| 비교 기준 | REST API | gRPC API |
| :--- | :--- | :--- |
| **성능 및 프로토콜** | • 주로 HTTP/1.1 기반<br>• JSON 형식을 사용하여 데이터양이 많으면 페이로드가 커짐 | • **HTTP/2** 기반으로 단일 연결에서 여러 요청 동시 처리<br>• **프로토콜 버퍼(바이너리)** 사용으로 페이로드가 작고 빠름 |
| **사용 편의성 및 디버깅** | • 익숙한 HTTP 메서드/상태 코드 사용으로 직관적임<br>• `cURL`, Postman 등으로 테스트와 디버깅이 쉬움 | • 바이너리 형식을 사용하므로 테스트와 디버깅에 **특정 도구**가 필요함 |
| **호환성** | • HTTP 기반으로 거의 모든 장치 및 **웹 브라우저**에서 폭넓게 지원 | • 기계 간 통신(M2M) 위주로 설계되어 **웹 브라우저에서는 직접 사용 불가**<br>• HTTP/2 미지원 환경에서는 제약이 따름 |
| **통신 방식 (스트리밍)** | • 단순 **요청-응답(Request-Response)** 방식 | • 클라이언트와 서버가 동시에 데이터를 주고받는 **양방향 스트리밍** 지원 |
| **주요 활용 사례** | • 인터넷에 노출되는 **공개 API (Public API)**<br>• 웹 브라우저 통신 및 **CRUD 기반 애플리케이션** | • **마이크로서비스 아키텍처(MSA)** 내부 서비스 간 통신<br>• 고성능 및 저지연이 필요한 **실시간 애플리케이션** |
