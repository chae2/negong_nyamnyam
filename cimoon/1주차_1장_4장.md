# 1장. 시스템 설계 기초 (숲에서 나무까지)

## 1. 데이터 흐름 (Data Flow)

데이터가 시스템을 통과하는 흐름 자체가 성능, 확장성, 사용성에 직결됨.

* **수집**: 실시간 스트리밍(Streaming)으로 받을지 vs 배치(Batch)로 모아서 칠지 결정.
* **저장**:
* 검색 빈도(Search frequency) 파악 필수.
* 데이터가 항상 일관되어야 하는지(Consistency 요구 수준) 따져봐야 함.


* **처리 (변환 / 분석 / 요약)**:
* 컴퓨팅 리소스 수요(CPU, Memory 등) 사전 계산 필요.
* 어디서 병목(Bottleneck)이 터질지 미리 고려해야 함.


* **검색**:
* 응답 시간(Response time) 단축이 생명.
* 캐시(Cache) 붙여서 I/O 줄이고 레이턴시 깎아야 함.
* 트래픽 몰릴 때 부하를 어떻게 쪼갤지(Load balancing) 고민 필요.



---

## 2. 확장성 & 장애 허용성 (Scalability & Fault Tolerance)

### 확장성 (Scalability)

* **정의**: 무작정 늘리는 게 아님. **'성능 저하 없이' 작업 부하를 처리해내는 능력**을 뜻함.
* **스케일업 (Scale-Up, 수직 확장)**:
* 그냥 서버 머리통을 바꾸는 거임 (UPGRADE).
* CPU, RAM, SSD 빵빵한 걸로 갈아 끼우기.


* **스케일아웃 (Scale-Out, 수평 확장)**:
* 똑같은 놈 여러 개 둬서 부하를 분산하는 거임. 클러스터에 인스턴스 계속 추가.
* 필수 고려 사항: 로드 밸런싱, 캐싱 계층, DB 샤딩/파티셔닝, Stateless(무상태) 서비스 설계.



### 장애 허용 시스템 (Fault Tolerant System)

* **정의**: 구멍가게처럼 에러 났다고 뻗는 게 아니라, '장애가 터져도 정상 작동을 유지하는 시스템'임.
* **핵심 지표**:
* 높은 신뢰성(High Reliability).
* 낮은 다운타임(Downtime: 서버가 죽어있던 시간 최소화).



> 🌲 **여기까지가 숲 (인프라/아키텍처 배치)**
> 🪵 **여기서부터는 나무 (세부 구현 및 최적화)**

## 3. 하위 수준 상세 설계 (Low-Level Design)

성능, 메모리 사용량, 코드 유지보수성을 고려한 구체적인 구현 단계.

### 알고리즘 & 복잡도

* 데이터 처리 및 문제 해결 과정.
* **시간-공간 트레이드오프**: 시간 복잡도를 줄이려면 메모리를 더 쓰고, 메모리를 아끼려면 연산 시간이 늘어나는 균형 맞추기 싸움.

### 자료구조 (Data Structure)

* 메모리 안에서 데이터를 어떻게 배치하고 운용할 것인가의 문제.
* 쿼리 성능과 메모리 풋프린트를 결정함.
* 자주 쓰이는 녀석들: Array, Linked List, Hash Table, Tree, Graph 등.

### API 설계

* 서로 다른 컴포넌트/서비스끼리 대화하기 위한 논리적 인터페이스.
* 일관성, 유연성, 보안, 성능 다 챙겨야 함.
* `v1`, `v2` 형태로 버전 분리해서 관리해야 기능 바뀌어도 하위 호환성 안 깨지고 유연함.

### 코드 레벨 최적화 기법

* **Refactoring**: 구조 개선으로 가독성/유지보수성 확보.
* **Loop Unrolling**: 반복문 분기 오버헤드 줄이기 위해 구문 풀어서 작성.
* **Memoization**: 이전 계산 결과 캐싱해 두고 재사용.
* **병렬 처리 (Concurrency/Parallelism)**: 멀티스레드/멀티코어로 동시에 작업 쳐내기.

# 2장. 분산 시스템 (Distributed System)

## 1. 분산 시스템의 필수 요건

* 일관성(Consistency), 가용성(Availability), 파티션 감내(Partition Tolerance)
* 지연 시간(Latency), 내구성(Durability), 신뢰성(Reliability), 장애 허용(Fault Tolerance), 확장성(Scalability)

---

## 2. 데이터 복제 및 동기화 (호텔 예약 시나리오)

> 상황: 복제 DB 포함 총 3개의 DB 노드가 있을 때, 모든 노드에 데이터를 똑같이 맞추는 방법.

### 복제 방식 분류

1. **앱 직접 쓰기**: 애플리케이션 레벨에서 3개 DB에 직접 꽂아 넣음.
2. **DB 자체 복제 (DB Replication)**: 마스터 DB가 받아서 복제본(Replica)들로 알아서 밀어줌.
3. **대리자(Broker) 기반 쓰기**: 중간 큐/메시징 계층을 두고 비동기로 싱크 맞춤.

### 쓰기 옵션 (Write Strategies)

* **직렬 동기 쓰기 (Serial Sync Writes)**:
* 3개 DB에 순서대로 쓰고 전부 확인(ACK) 떨어진 뒤 클라이언트한테 응답 날림.
* 안전빵이지만 레이턴시 늘어남.


* **직렬 비동기 쓰기 (Serial Async Writes)**:
* 메인 DB 1번에 먼저 쓰고 클라한테 바로 끝났다고 침.
* 나머지 2개 노드는 백그라운드에서 비동기로 천천히 업데이트. 빠르지만 싱크 깨질 위험 있음.


* **병렬 비동기 쓰기 (Parallel Async Writes)**:
* 스레드 자원 써서 모든 노드에 동시에 요청 날리고 응답 안 기다림.
* 처리량은 좋은데 실패 핸들링 골치 아픔.


* **메시징 큐 활용 (ex. Kafka)**:
* 클라는 카프카에 토픽만 쏘고 즉시 성공 반환.
* 컨슈머가 메시지 읽어서 각 DB에 적재하는 패턴 (※ 적어둔 '읽을 때 DB에 저장'보다는 '비동기 이벤트 파이프라인을 통해 최종적으로 DB에 안착시키는 형태'로 이해하는 게 정확함).



### 읽기 옵션 (Read Strategies)

* **단일 노드 읽기 (Read from One)**:
* 속도는 젤 빠름.
* 근데 아직 복제 덜 된 노드 찔렀을 때 과거 데이터 볼 수 있어서 정확성(정합성) 털릴 수 있음.


* **일부 노드 읽기 (Read from Quorum / ~50%)**:
* 과반수 이상 찔러서 데이터 비교 후 반환.
* 일관성과 속도 사이의 적절한 타협점 (트레이드오프 조율).


* **전체 노드 읽기 (Read from All)**:
* 3개 다 읽어서 가장 최신 버전 고름.
* 정확도는 확실한데 네트워크 I/O랑 시간 손해가 큼.

## 3. 일관성 (Consistency)

분산/복제 노드 환경에서 모든 인스턴스가 딴소리 안 하고 동일한 상태를 유지하도록 맞추는 개념.

* **정의**:
* 모든 노드가 항상 동일한 데이터를 바라보는 것.
* 동일한 업데이트 요청에 대해 모든 클라이언트가 **동일한 순서**로 반영된 결과를 얻는 것.



### 일관성 모델 분류

* **강한 일관성 (Strong Consistency)**:
* 쓰기 끝나자마자 어느 노드를 찔러도 무조건 최신 데이터가 반환됨.
* 정합성은 완벽하지만 동기화 대기 시간 때문에 레이턴시 올라가고 가용성(Availability)이 떨어짐.


* **약한 일관성 (Weak Consistency / 최종 일관성 - Eventual Consistency)**:
* 업데이트 직후엔 순간적으로 데이터가 안 맞을 수 있음.
* 일정 시간 지나면 결국 모든 노드가 동기화됨(Eventual).
* 레이턴시 낮고 가용성은 챙기지만 순간적인 불일치를 클라이언트가 감당해야 함.
