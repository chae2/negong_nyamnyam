### 5.2. 키-값 저장소

정의: 각 고유한 키가 특정값과 연결되는 간단한 데이터 저장 방식

저장 단위가 `키-쌍`

단순해서 RW 효율성 높음.

EX. 분산 딕셔너리, 분산 해시 테이블(DHT)

→ 키를 통한 데이터 저장/검색/업데이트가 가능.

→ 확장성, 성능, 유연성, 장애허용성 모두 굿. 왜냐면 분산도 쉽고(처리량 높이기 가능), RW 속도가 매우 빠르며 같은 노드에 있으면 더욱 빠르다, 데이터 형태 고정적x, 특정 노드에 장애 발생해도 접근할 수 있음

반정형 데이터 : json, xml 같이 자유로운 형식의 데이터

비정형 데이터: 사진, 동영상 파일

- 키 값 저장소 설계

  가장 먼저 해야 하는 것: 기능적 / 비기능적 요구 명확히 정의

    - 기능: put(저장), get(검색), delete(삭제)
    - 비기능: 확장성(새로운 데이터 추가 가능해야), 성능(put get에 대해 낮은 지연 시간 보장), 내구성(), 일관성, 가용성, 파티션 허용성

### 5.3. 확장성과 데이터 복제의 최적화

- 확장성 → 여러 노드에 나눠서 키값 데이터 저장하기. 수요에 따라 저장 노드 추가/삭제 자유롭게 해야 함.
- 상황: [나머지 연산] 노드에 대해 요청 분산을 나머지 기법(`% 노드 개수`)으로 사용할 때.
    - 과정
        1. 분산 기준 식별자 선택 (ex. 사용자 id, 세션 키, 클라이언트 ip)

           `해시(식별자)` ⇒ 특정 정수 형태의 해시값(여기서 `m` 이라 하겠음) 생성

        2. 나머지 연산: `m % 노드개수` 번째 노드에 요청 라우팅.

  → 비효율적인 부분: 노드 개수에 의존적임.

  → 해결: 일관된 해싱.

- [일관된 해싱]: 노드 개수를 상수인 `n`(해시 함수의 전체 출력 범위)으로 치환, 어떤 요청이 들어올 경우 `해싱(키) % n` 로 만든 숫자와 가장 가까운 인덱스의 노드로 라우팅.

  딱 맞게 안된다, 그래서 가장 가까운(오른쪽에 위치한) 애를 선택하는 방식.

  이때 n은 해시 알고리즘 비트 수로 고정이 된다. (ex.  32비트 정수를 반환하는 해시 함수(MurmurHash 등)를 쓴다면 $n = 2^{32}$가 되며, 해시 공간은 $0 \sim (2^{32}-1)$ 범위를 가짐)

  → 이것도 완벽한 방법은 아님, `핫 스팟(불균형)` 문제 발생 가능. 핫스팟: 특정노드가 과도하게 넓은 구간을 떠안는 것.

  → 해결: 가상 노드 사용

- [가상노드사용]: 물리노드가 2개, 가상 노드가 3개라고 하면 A-1, A-2, A-3, B-1, B-2, B-3 처럼 mn개씩 링 위에 늘어뜨려놓고 배치시키면 되니까 좀더 분산됨.

- 데이터 복제 전략
    1. 주종 모델 (primary-secondary)
        - 주: 쓰기 요청 처리
        - 종: 주의 데이터 복제 & 읽기 요청 처리

          쓰기 이후에 복제하므로 지연 발생.


        주에 의존적이므로 주저장소에 문제 생기면 쓰기 기능 X (근데 이건 종 저장소에도 의존적인 거 아닌가?)
        
        
        
        위 그림을 보면 주에 쓰기가 되고, 종에 복제 및 조회가 모두 이루어지는 의존적인 형태를 띄고 있음.
        
    2. 동등 모델 (peer-to-peer)
        
        모든 저장소 = 주, 쓰기 읽기 모두.
        
        모든 노드에 데이터 복제하는 것은 비효율적이라 노드 n개를 선택(>3≤5) 데이터 복제 처리. (n개 제외한 나머지 노드는 그 데이터를 영원히 동기화하지 않는다고 한다)
        
        즉, 특정 데이터 키 K는 오직 지정된 N개 노드에만 저장되는 방식을 채택한다. (카산드라, Dynamo)
        
        이게 partitioning. 데이터 K에 대한 책임지는 것은 링기준으로 결정된 N대뿐이다.
        
        N대 노드끼리의 동기화:
        
        - 읽기 복구: 읽다가 불일치 발견하면 백그라운드로 최신 데이터 업데이트
        - 안티엔트로피: 백그라운드가 머클트리 등을 비교하여 노드간 차이나는 데이터를 주기적으로 맞춤.
        - 임시위탁
        
        
        
    
    → 저자는 2를 추천.
    
    2의 장점: 지연시간 better, 가용성 유리함. (그냥 주에 의존하지 않아 단일 장애점 문제가 생길 일이 없어서 그런듯)

- 구체적 방식
    - coordinator: 특정 데이터 키 K를 책임진다. get(), put() 연산을 담당한다.

      K 할당받으면 시계 방향으로 N-1개 복제도 맡는다. 가상 노드 방식 채택 중이면 중복되는 것도 막는다.

      본인이 `우선 목록` 중 첫번째 노드임.


### 5.4. get()/put() 구현

- ‘구성 가능성’의 중요성: 밸런싱하는 능력. (가용성 - 일관성 - 비용 효율성 - 효율성 이런 특징들 있을때)
- 클라이언트 노드 선택:
    1. 일반적인 로드 밸런서 → 코드 종속 X

       해싱값 계산해서 자기에게 없으면 다른 네트워크로 보내버린다. 이과정에서 네트워크 불필요한 1홉 발생함.

    2. 분할 인식 클라이언트(개구리다;; **Partition-aware Client**) 라이브러리 사용 → 맥그라운드에 클러스터 정보(살아있는 노드, 노드당 해시범위 담당 범위) 동기화해서, 클라이언트가 데이터 요청 보내 → 키 K 기반 해시 계산해서 누구 담당인지 알게 됨 → 걔한테 바로 보내줘서 중간경유 필요 없음. 한번의 네트워크 통신으로 가능.

설명너무못한..다..

- 변수 두기: 이런 건 기준을 어케 정하는 것임?
    - r: 읽기 성공에 필요한 최소노드개수
    - w: 쓰기 “”

  → 읽기 쿼리 돌리면 r개의 노드에서 데이터를 읽어온다.

  r,w는 최소 한개 노드에서 둘다 맡게 만든다. 그래서 항상 최신쓰기데이터 접근 가능하도록

  r+w>n (강한일관성). 하나는 겹치니까 최소한 1개 차이가 나도록 만드는 거다. (비둘기집 원리)

  r+w≤n (최종일관성) 과거 데이터 읽을 위험 존재.

- R,W 크기 (기준)을 정하는 방법은 아래와 같음
    1. RW 중 어떤 작업이 많이 발생하는지 따라 w와 r 크기를 비대칭적으로 정한다
        - R 집약적 시스템: W=N, R=1

          오히려 R이 적네? 읽기 요청은 한대만 받아서 즉각 응답 받으므로 읽기 지연시간을 줄인다?

        - W 집약적 : R=N, W=1 혹은 둘다 1로.
    2. 장애 허용 범위 fault tolerance

       → r,w 클수록 살아있어야 하는 애들이 많아진다. 그럼 가용성 줄어드니까

       아래는 단순히 전체에서 성공에 필요한 스페어 애들을 계산한 것.

        - 쓰기 작업 견딜수있는 장애노드 수: n-w 대
        - 읽기 “ : n-r

       즉 n-w>0이어야 한다는 그런 의미 같다

    3. tail latency: 가장 느린 노드 응답 도착할 때까지 대기해야 하는.. 뭐라는 거야
- 강한 일관성 r+w>n 모델에서
    - get의 지연시간: r 개 중 가장 느린 애가 결정한다.

      **따라서 r이 많아질수록 일관성 > 가용성(응답속도)을 우선시하게 된다.**  (이거 저자가 잘못씀)


### 5.5. 키-값 저장소의 장애 허용성과 장애 식별

- 일시적 장애 관리
    - 쿼럼(최소투표) 기반 시스템: **살아있는 노드끼리만 표를 모아 시스템을 멈추지 않고 굴리기 위해** 사용하는 대표적인 장애 극복(Fault Tolerance) 기법

      쿼럼:  전체 $N$대 중 과반수($Q = \lfloor N/2 \rfloor + 1$)의 승인만 얻으면 연산을 통과

    - 그냥 쿼럼: 리더를 기준으로 중앙집중식으로
        - 문제 생길 때: 리더 뒤질 때 혹은 리더 ↔ 나머지 통신 안될 때
        - 문제 해결방법: 리더 죽었다고 선언하고 새 리더 선출 (비용)
    - ↔ 느슨 쿼럼: 비중앙집중식 (Dynamo, Cassandra)

      원래 데이터를 저장해야 할 정해진 서버 $N$대 중 일부가 죽었을 때, 시스템을 멈추거나 리더를 뽑는 게 아니라 **"해시 링에서 살아있는 아무 다른 노드(대타)**에 임시로 써두고 일단 넘어가자(Hinted Handoff)"라며 정족수 규칙을 대충(느슨하게) 만족시키는 방식

    - 예시

      **노드 5대 클러스터 ($N=5$, 쿼럼 $Q=3$)**

        - 쿼럼: 5대 중 **2대가 뒤져도**, 살아있는 3대가 투표에 참여해 과반수를 채우면 정상적으로 읽기/쓰기가 성공

          쿼럼은 **느리거나 죽은 노드를 기다리지 않고 버린 채 작업을 계속 진행**할 수 있음.

        - 전원 동의 모델(2PC): 5대 중 1대만 죽어도 전체 시스템이 멈춤(Blocking).
        - 느슨쿼럼: 5대 중 3대가 뒤졌을 때, 1대 모자람 - 해시링에서 살아있는 1대 아무나 가져와서 채우기

          (해시 링 상에서 [A, B, C, D, E] 바로 뒤에 있는, **원래 이 키의 담당이 아닌 정상 노드 'F'를 대타로 끌어오기)**

    - hinted handoff: 노드F는 이걸 자기 데이터로 보관하지 않고 원래 X의 것인데 내가 맡았다는 내용의 힌트를 달아서 보관하는것. 추후 살아났을 때 전달함.
    - sloppy한 이유: 클라이언트는 기본적으로 정식 담당 노드인 [A, B, C, D, E]를 찾아가서 읽으려 합니다. 그런데 최신 데이터는 엉뚱한 대타 노드인 F에 적혀 있으므로, $W + R > N$ 공식을 만족했음에도 불구하고 최신 쓰기 데이터를 읽지 못하는 상황(Stale Read)이 일시적으로 발생
- 영구적 장애 관리
    - 머클 트리: 복제품 사이의 불일치 빠르게 감지한다.

      ⭐ 단순 일치/비교만을 위해 해시를 써먹는다

        ```cpp
								[ Root Hash: H(1234) ]           <-- 최상위 머클 루트
                             /          \
                   [ H(12) ]              [ H(34) ]      <-- 부모 노드 (내부 노드)
                    /     \                /     \
                [ H(1) ]  [ H(2) ]     [ H(3) ]  [ H(4) ] <-- 리프 노드 (Leaf Node)
                   |         |            |         |
        // (이 아래는 트리에 포함되지 않음)
                Data 1    Data 2       Data 3    Data 4   <-- 실제 데이터 (Key-Value 등)
        ```

        - 리프노드: `해시(값)`
        - 노드 n의 부모노드: `해시(양쪽 자식값 더함)` 가짐 == 자식의 요약본

      해시는 그저 “입력이 1비트라도 다르면 완전히 다른 고정 길이 외계어(지문)를 뱉는 수학 공식”

      이걸 쓰는 이유? : 그냥 **“하위 데이터들이 변경되었는지 여부를 단 하나의 값으로 검증할 수 있는 지문”** 역할 을 하기 때문. 때문에 아래 데이터 중 한건만 바뀌어도 root hash가 아예 달라지기 때문에 DB 노드 A와 B가 서로 데이터 일치하는지 비교하는 데 탁월하게 빠르다..

        - 루트 비교 O(1)
        - 달라진 데이터만 이진탐색 O($\log N$) : 루트 다를 경우 왼쪽 오른쪽 비교해서 다른 쪽 브랜치로만 내려가서 구체적인 데이터 블록만 집어낼 수 있다.
- 장애 감지

  대부분은 ‘일시적인 장애’, 영구적인 문제가 아니니까 해시링에서 노드추가/제거는 신중하게 해라.

  노드추가/제거시 생기는일: 노드 구성 달라짐 → 노드에 변경사항 저장 → 가십프로토콜? 로 다른 노드와 동기화.

### 5.7. DynamoDB

- 정의: AWS에서 제공하는 비관계형 DB .. 대규모 트래픽 환경에서 데이터 양과 무관하게 한 자릿수 밀리초(ms) 지연 시간을 보장하도록 설계된 AWS의 완전 관리형 NoSQL(Key-Value 및 Document) 데이터베이스
